# 文档书写规范

> 目标读者：中文母语的产品、技术、设计团队成员。以下规范适用于所有正式产品文档（MRD、PRD、立项书、竞品分析、会议纪要等）。

---

## 1. 总则

文档的第一目的是让人看懂。三个原则决定所有细节：

| 原则 | 含义 | 自检问题 |
|------|------|----------|
| 清晰 | 不产生歧义，读者不需要"猜" | 换一个同事读，是否无需口头解释就能理解？ |
| 准确 | 事实和数据可追溯，判断和推测有标注 | 这个数字从哪里来？这个判断是基于什么？ |
| 简洁 | 删掉不增加信息的词汇和段落 | 删掉这句话，信息量有减少吗？ |

---

## 2. 语言规范

### 2.1 用词原则

**用日常语言说专业的事。** 目标读者是同行，不是搜索引擎。

#### 禁止使用的词汇类型

| 禁止类型 | 举例 | 替代方式 |
|----------|------|----------|
| 互联网黑话 | 赋能、抓手、闭环、打法、组合拳、对齐水位、底层逻辑、顶层设计、拉通、对齐、颗粒度、引爆点 | 用具体动作替代：不要写"赋能基层"，写"让区县文物局可以自己上传档案" |
| 技术黑话（非技术文档中） | 扩散模型、token 优化、向量检索、RAG pipeline | 用结果描述替代：不要写"基于 VLM 做多模态特征提取"，写"自动从照片中识别建筑物并分类" |
| 自创缩写 | MCG、DSF、PAP | 首次出现必须写全称。如果只用一两次，直接用全称，不要造缩写 |
| 空洞形容词 | 强大的、极致的、无缝的、全方位的、一站式 | 删掉，或用具体数据替代。不要写"强大的搜索能力"，写"支持按名称、位置、时期三个维度检索" |
| 冗余限定词 | 某种程度上、基本上、一般来说、大概率 | 删掉。如果确实不确定，标注"置信度：低"并说明假设 |
| 情感渲染词 | 令人震惊、史无前例、颠覆性、划时代 | 删掉。让事实和数据自己说话 |
| 自我吹捧与贬损竞品 | 遥遥领先、行业标杆、全面碾压、吊打、完爆、"竞品远远落后"、"竞品一无是处" | 用同一维度的可验证对比替代，己方与竞品的优劣都给证据。不要写"我们的识别能力碾压同类产品"，写"识别准确率 92%，同类工具 A 为 78%（测试集与口径见附录）" |
| 军事、武侠类词汇 | 攻坚、抢滩、狙击、集中火力、打赢、决胜、阵地、杀手锏、独门绝技、护城河、降维打击 | 用中性动词描述计划和优先级。不要写"集中火力攻坚识别模块"，写"本阶段优先开发识别模块" |
| 口语化表达 | 谁在疼、怎么凑合、痛点有多深、聊过、答不上来、做不下去、没人用、先去做再立项 | 用正式书面语替代。不要写"谁在疼"，写"目标用户与痛点"；不要写"怎么凑合"，写"当前解决方式"；不要写"聊过"，写"深度访谈过"；不要写"答不上来"，写"无法回答" |

#### 推荐使用的词汇类型

- **具体动词**：创建、删除、导出、对比、关联、上传、检索
- **可验证的名词**：用户数、响应时间、通过率、覆盖率、误差范围
- **日常连接词**：因为、所以、如果、但是、首先、然后

### 2.2 句式规范

- **一句话说一件事。** 超过 40 个字的句子，拆成两句。
- **主语明确。** 不用"被"字句模糊主语。不要写"数据被处理后"，写"系统处理数据后"。
- **肯定句优先。** 不要写"不是不重要的"，写"重要"。

### 2.3 中英文混排

- 中文和英文之间、中文和数字之间加一个半角空格：`用 Python 3.12 开发`
- 中文和全角标点之间不加空格
- 专有名词（公司名、产品名、人名）保持原样，不翻译：`SuperMap`，不是 `超图`
- 中文文档中用中文标点。引号用中文双引号，不用英文直引号 `""` 或直角引号 `「」`
- 英文单词在中文句子中不首字母大写（除非是专有名词）

### 2.4 标点使用

| 禁止 | 替代 |
|------|------|
| 破折号 `——` 滥用作停顿 | 用句号分隔完整的句子 |
| 波浪号 `~` 表示大约 | 用"约"或"左右" |
| 感叹号 `！` 渲染情绪 | 用句号，让事实本身传达重要性 |
| 省略号 `……` | 用"等"或直接列完 |

## 3. 段落与结构

### 3.1 结论先行

每个章节，结论句写在段首（第一句）。读者扫第一句就能判断要不要往下读。

结论句本身要简洁有力：一句写完，不加铺垫、不带空话。同一个结论在一个章节内只出现一次，不换措辞重复；后文如需回指，用交叉引用（如"见 §2.1 结论"）而不是复述。

```markdown
推荐选择方案 B，因为开发周期短且风险可控。
方案 A 功能更全但需要 2 倍开发时间，方案 B 在核心场景上满足需求，按 MVP 标准选 B。
```

### 3.2 段落长度

- 一个段落不超过 5 行（按编辑器宽度约 120 字符/行计）
- 超过就用换行分段。每个段落只讲一个点。

### 3.3 总文档长度

- MRD 正文（不含附录）：控制在 6-10 页
- PRD 正文（不含附录）：控制在 8-15 页
- 立项书正文：控制在 5-8 页
- 如果内容特别多，检查是否混入了实施细节（应该放到技术方案文档）

### 3.4 数字与度量

- 所有数字带上单位：`加载时间 < 2 秒`，不是 `加载时间 < 2`
- 金额标注币种：`375 万元`，不是 `375`
- 百分比标注基数：`用户留存率 60%（基准：注册后 30 天）`
- 日期统一格式：`2026-07-04` 或 `2026 年 7 月`

## 4. 引用与标注

### 4.1 数据引用

所有引用的数据点必须标注来源。不标来源的数字，读者视同猜测。

| 数据类型 | 标注方式 | 示例 |
|----------|----------|------|
| 公开数据 | 来源 + 年份 | `（国家文物局，2024）` |
| 内部数据 | 系统 + 时间段 | `（内部 CRM 系统，2026 Q1）` |
| 估算 | 显式标注 + 方法 | `（基于 [方法] 估算，置信度：中）` |
| 第三方报告 | 机构 + 报告名 + 年份 | `（艾瑞咨询，《XX 行业报告》，2025）` |

### 4.2 假设标注

任何未经验证的判断，必须标注"假设"并提供验证方式：

```markdown
假设：区县级文物部门有定期上报存档的制度要求。
验证方式：电话访谈 3-5 个目标区县的文管所负责人，确认工作流程和检查频率。
```

### 4.3 交叉引用

引用项目内其他文档时，用文档编号 + 章节：

```markdown
详见 02 MRD 第 4.2 节（核心场景）
```

## 5. 文档版本管理

### 5.1 版本号

- 草稿阶段：v0.1, v0.2, ...
- 评审通过：v1.0
- 后续修改：v1.1, v1.2, ...（小幅修改）；v2.0（重大修改）

### 5.2 文档状态

每份文档标注当前状态：草稿 / 评审中 / 已确认 / 已归档

## 6. 禁止文档元叙述

以下模式是文档写作者对读者的"旁白"，不增加信息量，必须删除。

| 禁止类型 | 举例 | 替代方式 |
|----------|------|----------|
| 方法论解释 | "按与闭环的距离分四层，主维度取与闭环的距离，理由是..." | 直接陈述分层结果。分层理由隐含在分层表中，不需要正文论述 |
| 章节功能说明 | "本节回答先实现什么""本文档回答市场值不值得做" | 删掉。标题已说明章节内容，不需要再向读者解释各节分工 |
| 写作过程暴露 | "先分流再写场景""本次验证的完整链路如图 1 所示""动作分析只覆盖..." | 删掉。直接给图表和数据，不描述分析和写作过程 |
| 自证式措辞 | "这印证了""这从技术上证实了""产品方向与官方标准同向""与...一致" | 删掉。事实和数据自身已说明问题，不需要作者出来盖章确认 |
| 内部管理笔记 | "此教训写入产品机制候选""本报告加 PNG 预览即为 30 秒可感知的案例页原料" | 删掉或移入项目笔记。正式文档正文不出现对文档用途的元评论 |
| 括号内的设计自评 | "（此时产品价值为规范出图模板，非识别提效）""（低分辨率照片可用于形制判断，不可用于细部）" | 如果这些判断重要，写成独立语句；如果不重要，删掉。不用括号夹带附加评论 |
| 冗余交叉引用链 | "假设1 到 4 见 02 MRD 表 11，验证市场与技术方向；本文假设验证用户与场景细节" | 只保留引用本身。删掉"谁验证什么"的职能划分说明 |
| "我们对现有文档的影响"式的自省 | 逐条列出本文档对已有文档的后续修订指令 | 正文只保留影响结论本身；修订指令是 to-do，不属于文档内容 |

### 6.1 文档不设头尾模板字段

- 不在文档开头放置"文档信息"表格（版本号、作者、状态、关联文档等字段）
- 不在文档末尾放置"修订记录"章节
- 版本号仅在正文标题行标注（如 `# 01 · 用户与场景分析`），不需要单开表格

需要版本追溯的 PRD 在第 1 节保留修订记录（无编号表格）。本项目 `文档/` 目录未纳入 git，不能依赖 git 历史追溯版本。评审纪要适用于多人评审场景。

## 7. 自检清单

提交文档前，逐条检查：

- [ ] 标题能看出文档类型和主题
- [ ] 每个章节的第一句是结论
- [ ] 所有数据有来源或标注为估算
- [ ] 所有假设有标注和验证方式
- [ ] 没有黑话、空洞形容词、情感渲染词、军事武侠类词汇
- [ ] 没有自我吹捧和贬损竞品的表述，对比结论都有证据
- [ ] 同一结论在一个章节内只出现一次，没有换措辞的重复
- [ ] 每段不超过 5 行
- [ ] 中英文之间有空格
- [ ] 没有破折号和「」
- [ ] 数字带有单位
- [ ] 有版本号
- [ ] 读一遍全文，能否删掉 20% 的字数而不影响信息量
