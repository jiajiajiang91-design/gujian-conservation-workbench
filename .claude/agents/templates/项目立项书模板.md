# 项目立项书模板（0→1）

> 适用场景：从零到一的新产品立项，团队规模小（2-5 人），核心目标是验证"有人用、愿意付费、能持续用"，而非交付完整功能集。
>
> 与成熟项目立项书的区别：更短（5-6 页）、更聚焦假设验证、不做三年收入预测、不做瀑布式里程碑。
>
> 立项书的作用有四个：让所有读者对项目目标达成一致；向资源授权人说明需要什么资源；说明项目最终能带来什么收益；提前列出可预见的风险和卡点。写每一节时对照这四个作用。

---

与现有方案的区别是 **[差异化，一句话]**。

## 3. 核心假设

> 0→1 立项不需要"证明市场存在"，需要的是列出关键假设并设计最低成本的验证方式。

| 编号 | 假设 | 如果错了意味着什么 | 验证方式 | 验证成本 |
|:----:|------|-------------------|----------|:--------:|
| H1 | [如：区县文物局愿意为电子档案付费] | [产品没有付费用户，商业模式不成立] | [如：找 5 个目标用户做深度访谈，确认预算来源] | [天/金额] |
| H2 | [如：AI 自动分类的准确率能达到 85%] | [人工校正量太大，效率提升微乎其微] | [用 50 份真实样本做测试] | |
| H3 | [填入你的假设] | | | |

**排序原则**：排在最前面的假设如果错了，整个产品方向就需要调整。这就是 MVP 要优先验证的东西。

## 4. MVP 定义

### 4.1 MVP 要回答的核心问题

## 5. 验证计划

### 5.1 分阶段验证

| 阶段 | 时间 | 做什么 | 要回答的问题 | 通过标准（Go/No-Go） |
|------|:----:|--------|-------------|---------------------|
| 问题验证 | 1-2 周 | [用户访谈/问卷/观察] | [用户真的有这个痛点吗] | [≥ X/5 用户确认] |
| 方案验证 | 1-2 周 | [原型 / landing page / demo 视频] | [用户愿意为这个方案买单/花时间吗] | [≥ X 个意向] |
| MVP 使用验证 | 3-4 周 | [可用的核心流程给真实用户用] | [有人真的用、真的付费吗] | [≥ X 个付费/活跃] |
| 下一步决策 | 1 周 | [汇总数据，决定继续/调整/放弃] | — | [见 5.2] |

### 5.2 Go/No-Go 决策标准（可选）

**继续投入的条件**（满足 2 条以上即可继续）：

- [ ] [如在 30 天内获得 X 个愿意付费的用户]
- [ ] [如核心功能的使用频率达到 X 次/周]
- [ ] [如用户主动推荐给同行]
- [ ] [填入你的标准]

**考虑放弃或大幅调整的信号**：

- [ ] [如连续两周无人打开产品]
- [ ] [如付费意愿为 0]
- [ ] [如核心技术指标（准确率/延迟）无法达到可用水平]
- [ ] [填入你的信号]

## 6. 资源与节奏

### 6.1 团队

| 角色 | 人数 | 投入方式 | 谁 |
|------|:----:|----------|-----|
| 产品 + 用户对接 | 1 | 全职 | [姓名] |
| 开发 | 1-2 | 全职 | |
| 设计 | 0-1 | 按需 | |
| 行业顾问（可选） | 0-1 | 按需咨询 | |

0→1 团队不超过 5 人。如果发现需要更多，检查是否 MVP 范围定大了。

### 6.2 节奏

| 节点 | 时间 | 交付 | 决策点 |
|------|:----:|------|:------:|
| 用户访谈完成 | [第 X 周] | [访谈记录 + 假设更新] | 是否继续 |
| 原型 / demo 可用 | [第 X 周] | [可演示的方案原型] | 是否有意向 |
| MVP 上线（第一个用户可用） | [第 X 周] | [可用的核心流程] | 是否有人用 |
| 第一次 Go/No-Go 评审 | [第 X 周] | [数据 + 结论] | 继续/调整/放弃 |

总周期控制在 **6-8 周**内（从立项到第一次决策评审）。超过 8 周说明 MVP 范围太大。

## 8. 风险

> 不可省略。提前列出的卡点有两个作用：资源授权人可以提前调配资源解决；风险真正发生时有据可查，不会被追责为"未预见"。

| 风险 | 类型 | 如果发生 | 预防方式 |
|------|:----:|----------|----------|
| [缺乏真实用户需求] | 市场 | [回到问题验证，重新理解用户] | [第 1-2 周先验证假设 H1] |
| [技术不可行（核心指标达不到）] | 技术 | [降级功能或用人工替代] | [技术预研在问题验证阶段同步做] |
| [竞品先一步上线] | 竞争 | [加速或找差异化切入点] | [定期关注竞品动态，但避免过度反应] |
| [填入你的风险] | | | |

0→1 阶段的首要风险是缺乏真实用户需求。所有计划围绕这个风险来设计：先验证用户是否有此需求，再验证方案是否被接受，最后验证技术是否可行。

## 附录：立项前自查（可选）

在提交立项书之前，确认以下问题：

- [ ] 和目标用户深度访谈过至少 3 人，确认痛点真实存在
- [ ] MVP 范围能在 4 周内开发完
- [ ] 第一个用户可以具体说出名字或单位
- [ ] 已明确停止或转向的判断标准
- [ ] 这份立项书不超过 4 页 A4（附录除外）

如果以上任何一条无法回答，先完成该条对应的调研工作，再提交立项书。
