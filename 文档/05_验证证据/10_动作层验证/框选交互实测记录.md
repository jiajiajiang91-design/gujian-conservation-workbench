# 框选交互实测记录

日期：2026-08-20。工作台 dev server 在 `127.0.0.1:5173`，浏览器面板驱动。
对象：Dai Loy 项目的现场照片（1029 × 782）。
依据：实施单元 02 框选修正接入的验收第 1、6、8、10 条。

## 一、结论

框选交互本身成立。拖动出框、位置引用显示、取消框选三步都按预期工作，取消后 chip、选框、输入框提示三处同时复位。

验收第 2、3、4、5、7、9 条要真实走一次助手回合，会发起模型调用，本次未跑，另行请示。

## 二、记录方式的两处限制

两条都影响证据强度，先写明。

**没有截图。** 浏览器面板未显示，页面不合成帧，`screenshot` 与 `left_click_drag` 都不可用。本次以 DOM 读数代替截图，记录的是元素的实际样式值与文本，不是渲染结果。像素级的呈现（选框颜色、透明度、位置引用的排版）未经目视核对。

**指针事件是页面内派发的。** `setPointerCapture` 要求活跃指针 id，合成事件没有，调用会抛 `NotFoundError`。测试期间把 `Element.prototype.setPointerCapture` 临时置为空函数，测完还原。因此本次验证的是 `handleDown`/`handleMove`/`handleUp` 三个回调与归一化计算，指针捕获本身未验证。指针捕获决定拖出图片边界后是否还跟手，这一条待截图可用时补测。

## 四、一处需要说明的观察

第一轮测试里位置引用显示的资料名与打开的资料对不上，chip 写的是相邻的另一份资料。复查后是页面状态漂移造成的：多次工具调用之间应用切换了项目与阶段，两次读数取自不同时刻的 DOM。刷新后把整个过程放进单次调用重跑，名称一致。

查表逻辑本身无误，`App.tsx:1983` 按 `imageSelection.evidenceId` 在快照的 `evidences` 里取 `title`。

## 六、顺带补上的防复发缺口

桩清单清空后，`action-delivery.test.ts` 原有四条断言全部落在空集上通过，不再能发现任何漂移。也就是说验收第 6 条在补测这一刻起就没有测试守着了。

补一条断言：登记表里每个 `executable` 且 `clientOp` 非空的动作，在适配器的 switch 里必须有对应 case。做法是给一组除 `getHead` 外触即抛的依赖，进了真分支必然碰依赖或提前返回，落到兜底分支则一个依赖都不碰、直接返回未执行文案，两者由此区分。另加一条遍历条数下限，防止这条测试自己变成空过。

自检：把登记表里 `ui:marquee-correction` 临时改成不存在的 clientOp，测试如实失败并指名动作；改回后转绿。自检过程中发现工作台读的是 `@gujian/domain` 的 dist，只改 src 不生效，需先 build。
