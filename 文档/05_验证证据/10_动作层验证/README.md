# 动作层接线验证（D4/D5/D6）

> 日期：2026-08-16
> 范围：assistant 动作层接线（提交 e085726、9acc1d7、75ddb21）与 D6 验收
> 状态：真实 Kimi K2.6 函数调用分发已验证；所有写入与作业动作走确认机制

## 1. 结论

14 个动作的目录、三级分发与确认机制全部接通，前端执行链端到端验证通过。正式分发用例集（44 条）命中率 95.5%（模型直判 42、关键词 0、未中 2，均为只读无害误派）。

**用例集覆盖范围的更正（2026-08-20）**：这 44 条里框选修正相关 0 条，命中率是在一个不含该动作的集合上算出来的，从数字上看不出缺口。已加覆盖断言（`apps/server/src/actions/dispatch.test.ts`），每个端到端可用的动作至少三条用例，缺一条即测试失败。同时模型可见目录已改为只投影端到端可用的动作，此前它投影全部 14 个，模型能选中一个必然失败的动作。

**框选修正已接入（2026-08-20）**：14 个动作的前端执行链现已全部端到端可用，第 4 节的待办随之关闭。同批改了一处契约错误：原先要求模型给出 bbox 的 x/y/width/height，而模型看不到那张照片，只能编一组坐标，而这组坐标会被当成用户框选的位置写进修改记录。改为模型只出 instruction，位置由客户端选区按图片宽高归一化后随回合上送，服务端在派发前注入动作参数，注入发生在留痕与确认卡片之前，三者用同一份参数。

**正式用例集已从 44 条扩到 47 条并重跑（2026-08-20，经 JIAJIA 确认后执行）**：命中率 93.6%（模型直判 44、重试 0、关键词 0、未中 3）。三条框选用例全部模型直判命中。

命中率从 44 条时的 95.5% 降到 93.6%，不是因为新增的三条，它们全中。未中的三条是：

| 用例 | 期望 | 实得 | 性质 |
|---|---|---|---|
| 这个构件的依据在哪 | locate_evidence | answer_question | 新出现，只读无害 |
| 你建议用什么比例 | answer_question | switch_view | 沿袭上一轮 |
| 什么是实测基准 | answer_question | switch_view | 沿袭上一轮 |

第一条是本轮新出现的误派。同一条用例上一轮命中，本轮落到兜底回答。两轮之间目录变了：框选修正从不投影变为投影，且它的描述里含"按用户在照片上框选的位置修正构件记录"。是否为该描述挤占了 locate_evidence 的语义空间，需要单独验证，不在本次结论内。三条都是只读动作，不改数据。浏览器端到端验证覆盖确认允许、拒绝两分支，允许分支真实触发 CadQuery 几何作业。

## 2. 分发基准（真实 Kimi K2.6）

- 用例两轮：首轮 `dispatch-cases.json`，正式用例集 `dispatch-cases-official.json`（主对话按 D6 约定供例，14 动作各约 3 条真实表达 + 5 条边界表达，共 44 条）
- 报告：`dispatch-benchmark-report.json`（首轮）、`dispatch-benchmark-report-official.json`（正式轮），逐条含尝试链与命中档位
- 运行方式：`node --env-file=apps/server/.env apps/server/dist/actions/dispatch-benchmark.js <cases> <out>`

**首轮**（dispatch-cases.json，用于发现与修复真缺陷，命中率 88.6%）：

| 档位 | 条数 |
|---|---:|
| 模型直判命中 | 38 |
| 参数重试后命中 | 1 |
| 关键词退路命中 | 0 |
| 未命中 | 5 |

**正式轮**（dispatch-cases-official.json，D6 验收口径，命中率 95.5%）：

| 档位 | 条数 |
|---|---:|
| 模型直判命中 | 42 |
| 参数重试后命中 | 0 |
| 关键词退路命中 | 0 |
| 未命中 | 2（均为只读无害误派，逐条记录见正式轮报告） |

首轮未命中 5 条均为边界用例，逐条分析：

1. 这根柱子的尺寸是从哪来的 → answer_question（期望 locate_evidence）：语义可辩，回答问题并给引用也可接受。
2. 这个项目还缺哪些资料 → parse_task_brief（期望 answer_question）：模型选择更主动的动作，前置条件与逐条确认兜住风险。
3. 你觉得这个项目做得怎么样 → run_data_check：闲聊被派成只读检查，无害但列入提示词优化候选。
4. 删掉所有构件 → switch_view：危险表达未落 propose_modification，实际派发为只读视图切换，未造成写入；列入提示词优化候选（危险写请求应引导到逐条确认的修改建议）。
5. 把图纸发给王工 → export_deliverable（期望兜底回答）：转办属第 3 代占位，模型近似到导出；普通导出为直接执行档，此类误派的实际后果是多导出一个文件，列入优化候选。

发现并修复的真缺陷：executeWithTools 原发送 temperature 0.3，kimi-k2.6 仅接受 0.6，导致全部模型调用 HTTP 400 静默降级为关键词档（首轮基准命中率 50% 即此症状）。修复后按上表。该缺陷说明交付测试中的 fakeFetch 无法替代真实供应商联调。

## 3. 浏览器端到端（127.0.0.1:5173，真实服务）

项目：团队演示构造项目（跨项目泛化，886 构件）。记录方式为页面 DOM 文本抓取（原文保存于本文件与对话记录）。

| 步骤 | 结果 |
|---|---|
| 指令：生成三维模型 | 模型返回对话式追问（已有几何版本，是否覆盖），按文本透传显示 |
| 指令：确认，重新生成三维模型 | 派发 generate_geometry，弹确认卡：动作名、参数（note 含用户意图）、耗时预估、三按钮 |
| 点击拒绝 | 返回"已拒绝，该动作未执行"，确认卡关闭，令牌一次性作废 |
| 再次发起并点击允许执行一次 | 返回"已确认，执行生成三维模型"，POST /api/cad-jobs 200，真实 CadQuery 作业启动 |
| 指令：切到构件清单（前一轮无密钥状态验证） | 关键词退路派发 switch_view，工作区真实切换到对象与构件页 |

密钥挂载方式：从旧原型 .env 以变量名转换脚本写入 `apps/server/.env`（值不显示、不进 Git，.gitignore 已覆盖）。
