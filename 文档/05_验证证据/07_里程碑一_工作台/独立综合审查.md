## 2. P0 问题

### M1-AUD-001：独立 JSON 包错误声明二进制仍可用

**原等级：P0；当前状态：已关闭**

`ProjectPackageService.exportJson()` 将仓库中的资产记录原样写入 `project.json`。原始资产记录的 `contentStatus` 为 `available`，但独立 JSON 不携带二进制文件。因此，导出的 JSON 本体仍声明资产可用，与实际包内容不符。

现有导入逻辑会在导入后根据 `parsed.contents` 把状态改成 `missing`，所以浏览器回导后的页面和测试显示“缺失”。这只能证明回导结果被修正，不能证明导出的 JSON 自身诚实声明了二进制缺失。

证据：

- `packages/infrastructure/src/project-package-service.ts:89`：独立 JSON 导出入口。
- `packages/infrastructure/src/project-package-service.ts:105`：资产记录使用 `{ ...record }` 原样写入，未按独立 JSON 的内容边界改为 `missing`。
- `packages/infrastructure/src/project-package-service.ts:111`：ZIP 当前复用独立 JSON 的序列化结果，需要在修复时区分两种包的内容语义。
- `packages/infrastructure/src/project-package-service.ts:210`：只有导入阶段才根据实际携带内容改写状态。
- `packages/infrastructure/src/evidence-ingestion-service.test.ts:57`：测试只断言导入后的状态，没有断言导出的 JSON 本体。
- `文档/05_验证证据/07_里程碑一_工作台/milestone-one-browser-run.json:92`：当前证据记录的是空库回导后的缺失数量，不能替代对导出文件本体的检查。

影响：

- 独立读取 `project.json` 的人员或程序会得到错误的资产可用状态。
- 数据真实性不满足本次限定审查中的“JSON 诚实声明二进制缺失”。
- JSON 与 ZIP 的内容边界没有在导出数据契约中明确表达。

最小修复范围：

1. 在项目数据序列化时显式区分独立 JSON 与含二进制 ZIP。
2. 独立 JSON 中未携带的资产必须写为 `contentStatus=missing`。
3. ZIP 内 `project.json` 的状态必须与 ZIP 实际携带并通过哈希核对的文件一致；不得因复用独立 JSON 而错误写为缺失。
4. 增加导出本体测试：在导入前直接解析独立 JSON，断言资产为 `missing`；同时断言 ZIP 回导后真实文件为 `available` 且哈希一致。
5. 修复后重新完成一次浏览器 JSON/ZIP 空库回导，并更新对应证据摘要。

除上述范围外，不扩大修改。

修复提交：`19eeef4 fix(projects): declare json assets missing`。本报告第 5 节记录唯一一次针对性复核结果。
