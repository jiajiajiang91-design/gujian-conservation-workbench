# 02 · 开源技术借鉴研究 v1.0

> 本文合并原 03 开源 agent 技术借鉴、04 开源代码借鉴与现状评估两份研究记录。研究时点为 2026-08-14 与 08-15，结论已进入技术架构第 5 章与第 7 章，本文保留对照过程与源码出处。文中描述的实现状态为研究时点状态，当前状态见 [技术架构](../02_技术/01_技术架构.md) 第 2 章；文中 13-x 与 H 编号为研究时点的旧文档编号，现行文档对应关系见 [00 索引](../00_索引.md)。

## 1. 结论

deepseek-harness 的价值不在架构而在五条可移植的设计原则：模型可见字段与程序执行字段严格分离；确认结果是封闭集合且异常一律按拒绝处理；软性引导与硬性强制分层且互不读写；全部行为落在只追加的事件日志上；参考指令按目录加载。

开源代码研读的结论是域模型的严谨度已超过全部开源参照，真正的缺口是四块：AI 动作层、规则层、受控词表、曲线表达。这四项现已分别落入技术架构 7.6 助手动作分发、5.5 规则集与求值器、5.6 受控词表与 5.7 形制参数层。

## 3. deepseek-harness 对照研究

### 3.1 动作怎么定义

结论：表 10 的五个字段（动作、触发方式、前置条件、确认级别、留痕）覆盖了业务侧，缺的是接口侧的三样东西：参数定义、结果结构、失败行为。harness 的工具定义把这三样作为必填项。

#### harness 的做法（来源：docs/subsystems/tools.zh.md，源码 packages/core/tools/src/index.ts）

1. 一个工具由两部分组成。模型可见部分只有三个字段：名称、描述、参数 schema，经白名单投影后进入模型请求。执行部分（执行函数、输出契约、超时、并发标记、界面展示回调）永不发给模型。
2. 参数有类型化 schema，框架代为校验。参数不合规不执行动作，返回结构化错误 INVALID_ARGS 给模型，模型据此自行重试。没有关键词退路这一层。
3. 输出也有契约。每个工具必须声明输出 schema，执行结果不合规同样按错误处理（INVALID_TOOL_OUTPUT）。结果里模型可见内容与程序使用的规范值分开。
4. 参数一旦进入流水线不可改写，理由写得很明确：历史记录、审计、界面展示和实际执行必须看到同一份参数。
5. 未知动作返回结构化错误 UNKNOWN_TOOL，调用失败但对话不中断。

#### 与表 10 逐字段对照

| 表 10 现有字段 | harness 对应物 | 判断 |
|---|---|---|
| 动作、触发方式 | 名称 + 描述（模型靠描述路由） | 已覆盖。触发方式本质是描述的一部分 |
| 前置条件 | guard（程序化校验，只能拒绝不能放行，见对照二） | 表述在，但需改写为可程序校验的条件 |
| 确认级别 | 审批 seam（见对照二） | 已覆盖，需补异常默认行为 |
| 留痕 | 事件日志（见对照三） | 已覆盖，需补模型原文留存 |
| （缺）参数定义 | 类型化参数 schema + 校验 | 表 10 需新增。例如"生成修改建议"的参数是哪几个字段、哪些必填 |
| （缺）结果结构 | 输出契约 + 模型可见内容与程序值分离 | 表 10 需新增。每个动作执行完返回什么结构，供界面渲染和留痕 |
| （缺）失败行为 | 结构化错误回给模型重试 | 表 10 需新增。参数错、前置不满足、执行失败各自返回什么 |

#### 对关键词退路的重新定位

13-6 现文写"模型将用户表达映射到清单动作，失败时退回关键词匹配"。harness 的做法提示了一个更细的分层：模型输出格式错误或参数不合规时，第一选择是把结构化错误回给模型重试一次，重试仍失败才落关键词匹配；模型服务整体不可用时才直接走关键词。理由是模型自我纠错的成功率远高于关键词对自然语言的覆盖率。这是设计判断，标注为假设，验证方式是动作分发实现后用同一批真实用户表达对比两种退路的成功率。


### 3.2 执行前确认与留痕

结论：表 10 的确认级别缺两条规则，一是异常情况的默认行为，二是授权的作用范围。harness 的审批设计恰好补上这两条，并且直接印证了"浏览不设硬锁、停靠点只管写入和推进"的分层。

#### harness 的做法（来源：docs/subsystems/approval.zh.md、plan.zh.md、permission-presets.zh.md）

1. 确认结果是封闭集合：允许一次、拒绝、撤回、通道不可用，共四种。除"允许一次"外全部按拒绝执行。确认弹窗没弹出来、用户关掉页面、程序异常，都不会放行动作。文档称之为 fail closed。
2. 一次授权只放行被询问的那一个动作。不存在"这次同意了就默认后面都同意"的隐式升级；要放宽只能显式切换会话级策略，且切换本身记入日志。
3. 每次确认在日志里留两条成对记录：询问一条、决定一条，用同一个请求 id 关联。程序崩溃时留下"有询问无决定"的可检测状态，不会出现凭空产生的决定。
4. 确认请求不复制动作参数，只引用已经展示给用户的那次调用。避免弹窗里的参数副本与实际执行的参数漂移。
5. 软硬分层：计划模式（相当于流程引导）是纯软性提示，只改系统提示词段落，不增删动作目录，也不做任何强制；真正的强制由沙箱和审批两个独立开关承担，三者互不读写。进出计划模式时动作目录保持不变，避免模型因目录变化而困惑。
6. 权限预设：把多个独立开关打包成具名档位（例如"工作区可写 + 逐条确认"），用户选档位，程序拆开写入各开关，档位选择本身也记日志。

#### 对古建的映射

1. 表 10 的"逐条确认"需要补一句：确认通道异常时按拒绝处理，且一次确认只对当前这一条建议生效。这两句现在不写，实现时就会被默认成宽松行为。
2. "推进流程"动作在停靠事项未清时"拒绝并说明原因"，这个语义与 harness 的 guard 一致（guard 只能拒绝、不能放行，多条 guard 里任何一条拒绝即拒绝）。可以明确为原则：前置条件全部实现为程序校验，模型无权绕过。这正是辅导 11 "确定性要求迁移到规则或脚本"的具体形态。
3. 浏览引导与写入确认分层：浏览环节的引导（该看什么、下一步去哪）做成提示层，不锁任何动作；写入、推进、签发做成确认层，走留痕。环节切换时动作清单不增删，用前置条件控制可用性。这与 13-6 现有设计方向一致，harness 提供的是"两层互不读写"这条更严格的边界。
4. （可选）toB 角色档位：测绘员、审核人、项目负责人各对应一组确认级别配置，用户按角色选档，程序拆开落到各动作。属于 PRD 阶段议题，第 1 代六动作不需要。


### 3.3 上下文管理与长对话

结论：harness 把"只追加的事件日志"作为唯一真源，模型上下文和界面展示都是日志的派生视图，这个概念与档案行业对过程真实性的要求天然契合，值得作为古建留痕设计的统一原则；压缩和按需加载两项机制当前用不上，但其中两条原则应现在定下。

#### harness 的做法（来源：docs/subsystems/session.zh.md、compaction.zh.md、skills.zh.md）

1. 会话是只追加的事件日志，带连续序号。模型消息历史从日志派生，从不单独存储；每个模型请求的完整信封（配置、系统提示词、工具清单）也记入日志，因此任何一次请求都可以从日志完整重建。
2. 模型请求的动作调用以原文记录：模型输出的参数 JSON 字符串一字不改存档，解析在存档之后。解析失败也能追溯模型到底说了什么。
3. 长对话压缩：摘要替换模型可见的历史区间，被替换的原始事件仍留在日志里（称为被遮蔽）。压缩操作本身用成对的开始与结束事件括住，中途崩溃留下可检测的未闭合标记。
4. 参考指令（skill）渐进加载：模型上下文里只放目录（名称加一句描述），正文在模型点名时按需读取，每次读取都取当前最新版本。

#### 对古建的映射

1. 统一留痕原则：AI 对话、动作执行、确认询问与决定、流程推进，落到同一条项目内只追加的事件流上，事件带序号和时间，成果版本引用事件区间。当前工作台的修改历史、调用记账、GeometryRevision 分开存放，概念上先统一（是否物理统一是架构问题，留到 PRD 后）。产品叙事上这一条有独立价值：文物归档本身要求全程可追溯，事件溯源等于把档案学的过程真实性做进产品底座。
2. 调用记账应保存模型原始输出原文，解析后的结构另存。现在就能定的原则，成本低。
3. 两条现在就该定的压缩原则（实现可以推迟）：原始记录只从模型上下文移除、永不从项目留痕删除；任何压缩或整理操作自身留痕。
4. 场景文件按需加载：古建 agent 的测绘规范、构件词表、成果模板等参考材料拆成场景文件，主提示词只放一行目录，按环节读取。这是辅导 11 "按工作场景拆分参考文件"的现成参照实现，也是 Agent 定义做减法的具体做法。


### 3.4 不建议照搬的部分

结论：harness 是面向开发者的通用 agent 平台，以下机制服务于它的通用性，古建 agent 是单一垂直场景，照搬会违背 0 到 1 最小实现原则。

1. 插件架构（Cordis、能力 seam、声明合并）：解决"任何能力都可替换"的平台问题，古建不需要。
2. 作用域分层（scope、子 agent 的工具继承与遮蔽）：多 agent 调度的基础设施，是否拆多 agent 本身在辅导 11 中已明确不预设。
3. 并发调度（并行工具组、独占屏障）：第 1 代六动作串行执行即可。
4. Code Mode、沙箱执行、MCP 接入：与古建动作清单无关。
5. 压缩的完整实现（token 压力测量、工具结果修剪）：古建单次工作会话的对话量远未到需要的规模，只取第 3.2 节两条原则。


## 4. 开源代码深读

### 4.1 声明式规则层（来源：ssffd/jiangshu；yxk925/ACA-Builder 的 const.py）

结论：规则层的三个设计问题（规则怎么表达、来源怎么标、多规范怎么并存）在两个参照里都有可直接采用的答案。

参照实现细节：

1. 规则表达（jiangshu `formulas.json`）：三层 JSON，构件、维度、公式字符串。公式以基准参数表达并支持跨构件引用：檐柱 `height: "11*D"`；金柱高 `column_yanzhu_height+5*langbujia`；单步梁宽 `4/5*beam_shuangbu_width`。无法公式化的维度写"按实计"，程序识别后要求实测输入。基准变量单独放 `variables.json`（D=300，cun=32 并注明"清代营造尺32mm"）。
2. 举架算法（jiangshu `JiangSuan_v1.0.py` 第 159 至 260 行，注意：v1.0 求值逻辑是硬编码，formulas.json 是尚未接线的数据底座，借鉴时取两者之长）：步架数 =（檩数-1）/2；均分步架 = 通进深/2/步架数；举高按系数递增（五举 0.5、六五举 0.65、七举 0.7、八举 0.8、九举 0.9，檐步到脊步逐架变陡）；大式檐步架 = 4 或 5 倍檐柱径。关键模式：同一输入输出多个并列方案（平缓五举、标准七举、陡峻八举各算一遍）供人选择。
3. 来源标注与偏离记录（ACA-Builder `const.py`）：每条权衡常数的注释带文献出处和取值理由，实例：中槛高度 0.5 柱径并注"汤崇平书p20中定为0.64"；抱框宽度注"梁思成和马炳坚给出2/3D，汤崇平给出0.64，姜振鹏给出0.56，实际看来0.56的观感更好"。即规则允许偏离文献，但偏离本身连同理由被记录。
4. 多规范并存（ACA-Builder `const.py` 第 222 至 225 行）：举架系数存四套并按来源命名，LIFT_RATIO_DEFAULT [0.5,0.7,0.8,0.9] 注"梁思成图纸中采用的系数"，LIFT_RATIO_SMALL [0.5,0.65,0.75,0.9] 注"清工程做法则例的推荐系数"。规范差异表达为并存的规则集。

对工作台的设计建议：

- 规则文件格式（候选，供架构评审）：每条规则含 ruleId、subjectComponentType（词表引用，见 3.5）、dimension、formula、baseParams、source（文献加页码）、deviation（偏离值与理由，可空）、applicability（形制、大式小式）。规则是数据文件，专业人员逐条可审，每条可标注规范出处，直接满足项目"数据必须标注来源"的约束。
- 求值器要求：跨构件引用需按依赖排序求值；"按实计"标记映射到现有 UnknownValueSchema 的 reasonCode（缺口 2 与已有未知项机制在此接通）；求值运行走 ProducerRef 已预留的 rule 态加 ruleRunId 留痕。
- 两个用途：修改建议的合理性核对（计算值加容差带，超出即提示，表 10 已有此要求）；无实测构件的公式推测（与对称推算并列，producer 标 rule，人工确认后转 human）。
- 多方案输出对接停靠点：规范选择类停靠（表 6 第三类）的选项生成可直接用多规则集并列计算，每案附系数出处，正是 jiangshu 的输出模式加 ACA 的来源标注。
- 边界：jiangshu 只覆盖清式无斗拱小式，数值不可照搬；ACA-Builder 未见许可证文件，默认保留所有权利，只参考思路与数值出处，不复制代码。

### 4.2 形制参数层与模板往返（来源：ACA-Builder 的 template.xml 与 template.py）

结论：一栋清官式建筑用约 60 个参数加两张拓扑网表完整描述，且模板支持从活对象序列化回 XML 的完整往返，这是辅导 11 数据模型与导入导出要求的现成参照。

参照实现细节：

1. 模板参数（`template/template.xml`）：斗口 DK=0.08 为模数根；面阔进深逐间给值（x_rooms=3，x_1=6.16 至 x_4）；柱高柱径；斗拱选型与间距；屋顶形式枚举；椽架数；翼角起翘 qiqiao、出冲 chong、推山 tuishan、收山 shoushan、举折 juzhe 全部是参数；瓦作尺寸。
2. 拓扑网表：柱网 `pillar_net` 用网格坐标串（`0/0,0/1,...`），枋连接 `fang_net` 用柱对串（`0/0#1/0` 表示两柱间有枋）。拓扑与尺寸分离，改尺寸不动拓扑。
3. 模板往返（`template/template.py`）：loadTemplate 解析 XML 写入对象属性集，saveTemplate 从活建筑对象反向序列化回 XML（第 638 至 768 行，逐属性生成节点含列表嵌套）。用户改完参数可另存为新模板，模板即项目数据文件。
4. 权衡传播：属性集分场景级与对象级（`data.py`，Scene.ACA_data 与 Object.ACA_data），斗口改动经权衡算法传播到全部构件。

对工作台的设计建议：

- 数据模型候选结构（标注为假设，进 PRD 数据模型章节由 JIAJIA 拍板）：在现有逐构件实体（实然值，实测与证据约束）之上增加形制参数层（应然值，ACA 式模板参数加网表），两层之差即现状测绘要记录的变形、残损与历史改动。这同时是 v3 保真度问题的架构级解法方向：精细形制由参数层表达，实测差异由实体层覆盖。
- 现有 ProjectDrivenGeometrySpecSchema 已经是项目驱动路线，候选做法是在其上补一个 archetypeParams 区段。
- 拓扑网表与现有 GeometryInterface 互补而不冲突：网表是设计拓扑（应然，轻量），interface 是实测接口（实然，带容差），对照两者即可发现结构异常。
- 模板往返对应辅导 11 "支持导入、选择和导出结构化项目数据"，当前工作台已有 ZIP 导入导出，缺的是"从当前项目另存为可复用模板"，可作第 3 代动作候选。

### 4.3 规则驱动位姿与装配校验（来源：Optimus25564/dougong-foguang）

结论：15 件构件的整朵斗栱位姿由 8 个规则常数加 3 个推导函数生成，不存一个手填坐标，这是推测构件位姿生成的参照实现。

参照实现细节（`src/content/placements.js`、`src/content/parts.js`、`src/interaction/snapValidator.js`）：

1. 常数只有 8 个：每跳出挑 20 分、足材广 21、单材广 15、小斗高 10 耳 4、栌斗高 20 耳 8、下昂斜度 10 度、耍头斜度 5 度、搭接压紧 4 分。
2. 推导函数三个：pingTop（斗平面高 = 斗心 + 高/2 - 耳 - 搭接）、douOn（斗坐栱顶）、drop（斜构件跳头下沉 = 跳距乘斜度正切）。全朵位姿是这三个函数自下而上的链式调用（栌斗斗平 P0 到华栱一到交互斗一到 P1，逐层叠加），源码注释明言"按分°规则生成位姿而非手填坐标，改这几个规则常数即可整体调整，所有构件自洽联动"。
3. 构件字典强校验：REQUIRED_FIELDS 12 个字段（id、名称、术语、拼音、尺寸、卷杀瓣数、层级、parents、职责、描述、掌故、受力动画开关），缺字段即报错。
4. 装配校验：validateSnap 按 0.12 米容差判断构件是否放到位。

对工作台的设计建议：

- 推测构件的位姿生成用同一模式：从已确认锚点（实测柱位）加形制规则推导，不复制对称构件坐标再手调。生成结果 producer 标 rule，与 3.1 的规则层共用求值通道。
- 容差校验模式可用于框选修正后的位置合理性核对：新位置与规则推导位置之差超容差即提示（不阻断，浏览不设硬锁原则）。
- parts.js 的 role（承托职责一句话）与 desc（专业描述）字段是构件词表条目的知识字段样例，对接 3.5 词表与 H6 场景文件。

### 4.4 曲线体素（来源：in-a-mist/miniLibs 的 Column.cs）

结论：连续变截面（收分卷杀）用十几行控制点定义加旋转成面即可表达，补上这类体素后 v3 的柱形精细度才能进入成果链。

参照实现细节：柱顶 4 份收分用三点控制曲线过渡，柱身用六点插值曲线（半径在 8/9、7/9、2/3、1/3 高度处渐变），两段拼接后绕 Z 轴旋转成面得实体；材份单位 F 由注入的 ICalculatorRule 提供，几何代码不含任何规范数值。

对工作台的设计建议：

- solid 判别联合增加旋转轮廓体素（候选形态：kind 为 revolvedProfile，profile 为 [半径, 高度] 点列，axis 与 centerMm 同现有约定），向后兼容，现有三种体素不动。CAD worker（Python 侧）对应增加该体素的求交与投影支持。
- 规则注入模式（ICalculatorRule）与 3.1 的规则集对应：清则例、营造法式、地方做法是同一接口的不同规则集，几何生成按 ruleSetId 取值，为跨形制泛化（T12 verified 的方向）预留。
- 批次：可选，随图纸构件画法或 v3 精细度后续需求触发，不主动做。

### 4.5 受控词表（来源：Arches 的 RDM；需求实证来自 jiangshu 的 aliases.json）

结论：componentType 需要从自由字符串升级为受控词表引用，同物异名是真实存在的行业现状，参照两处证据。

参照实现细节：

1. Arches 参考数据管理器（RDM）：词表符合 SKOS 标准（概念含首选标签、替代标签、broader/narrower/related 关系），授权用户更新条目，概念直接绑定到数据录入表单供选择（来源：Arches 官方文档 overview，2026-08-15 访问）。
2. 同物异名实证（jiangshu `aliases.json`）：行业写法本身就带别名，檐柱又称小檐柱、金柱又称老檐柱、月梁又称顶梁。30 余个构件名几乎条条有别名。自由字符串下这些会成为不同的 componentType，跨项目复用与统计全部失效。

对工作台的设计建议：

- 词表条目候选结构：conceptId、prefLabelZh（首选名）、altLabels（别名列表）、broader（上位概念，如檐柱属柱）、source（术语出处）、confirmedBy（确认人 actorId、decisionId、理由、时间，复用 HumanProducer 既有形态）。
- componentType 迁移路径：兼容期双写（保留字符串字段、新增 conceptId 引用），新数据强制走词表，存量数据批量映射后收口。
- 旅程第五步的形制入库即词表操作：王工确认五铺作单杪单昂，就是新增或引用一个词表条目并挂确认记录；后续项目复用即引用同一 conceptId。
- 词表条目的知识字段（role、desc，见 3.3）同时服务 H6 场景文件与"回答问题"动作。

### 4.6 识别上限与评测方法（来源：LTTM/Scan-to-BIM；LydJason/BIMNet）

结论：拿到两个可直接使用的东西，一个数字和一个评测框架。

参照细节：

1. 数字：点云构件语义分割的学界最好水平，BIM-Net++ 在 HePIC 数据集 mIoU 43.7%，优于 SegCloud、Cylinder3D、RandLA-Net、PVCNN 四个对比模型（来源：LTTM/Scan-to-BIM README，2026-08-15 访问）。
2. 评测框架（BIMNet，AUTCON 2025）：14 个基于 IFC 标准的构件类别；人工在 Revit 建高保真基准模型作对照；指标同时覆盖几何与拓扑两个维度（重建模型的几何精度和拓扑正确性分开评）。

对工作台的设计建议：

- mIoU 43.7% 加出处写入 13-2 能力边界，替换定性表述；求职答辩"为什么不做全自动"的一句话答案。
- 模型测试集（辅导 11 任务）采用几何加拓扑双维指标：几何维度评尺寸误差与命中率，拓扑维度评接口判断正确性。现有 GeometryInterface 使拓扑评测天然可行，这是多数研究项目做不到的。评测粒度按构件类别统计命中、存疑、误识别三档。

### 5.2 定义一次到位，实现分批，暴露只含已实现

结论：21 个动作在设计层一次全部定义完（H1 修订时全部入表 10，每个都补齐八字段），实现分两批，模型可见目录任何时刻只包含已实现动作。

这个拆法对照了 dsh 的实际做法（来源：docs/tool-catalog.zh.md 与 docs/subsystems/skills.zh.md）：dsh 全目录有 45 个以上模型可见工具，全部按同一契约定义，但没有任何部署全暴露；每个部署通过插件组合与工具限制裁剪出自己的子集，个别插件出厂即标记禁用，启用需显式选择。它分的是暴露，不分定义。古建照此办理：定义不分代（避免表 10 反复返工，也让确认级别和留痕设计一次想全），实现按就绪度分批。

实现批次的划分依据是项目内约束，与 dsh 无关：第 2 代 7 个（序 3、4、15 至 19）后端能力已存在或模型即可完成，属于主线演示闭环；第 3 代 8 个需要新建后端能力或协作机制，按辅导 11 的顺序在 PRD 与架构确认后实现。第 2 代上线时模型可见目录共 13 个动作；第 3 代动作在表中标注未实现，不进模型目录，避免模型调用注定失败的动作。

### 5.3 永不给模型的操作

以下操作不进任何一代动作清单，只保留人工入口，理由是专业责任或留痕完整性：

1. 正式签发。表 6 停靠点已规定只有责任人可操作。
2. 删除项目或清空数据库。
3. 修改留痕记录与确认记录。留痕只追加，与第 3.2 节原则一致。
4. 修改原始证据文件。
5. 指定或变更责任人。任务卡人工操作。

### 5.5 补充判断

1. 修改参数不单设动作。用户说"把柱径改成 300"路由到动作 5 生成修改建议，程序合理性核对后逐条生效。绕过该流程的直接写入会破坏已通过古建专业审查的留痕设计。
2. 高成本动作（15、16）两条通用规则：执行前展示预估（生成作业实测约 4 分钟量级，来源：执行会话 2026-08-14 运行记录）；执行中可取消。作业失败将结构化原因回给模型组织说明，不自动重试。
3. 目录保持稳定：13 个动作全程对模型可见，环节切换不增删目录，不可用时由前置条件拒绝并说明原因。这是 harness 计划模式的做法（进出模式不改工具目录），避免模型因目录变化而路由混乱。
4. 13 个动作的路由准确率是一个风险，标注为假设：辅导 11 提示词做减法的原则同样适用于动作描述，每个动作描述控制在两句内。验证方式即 H4 验收的分发测试，测试集需覆盖全部 13 个动作各至少三条真实表达，并加入 5 条应落到"回答问题"的边界表达。
5. 分工边界不因动作扩展移动：AI 触发作业、组织说明、提出修改；实测录入的最终确认、专业存疑判断、签发仍由人执行。写进 13-2 分工表述即可。
