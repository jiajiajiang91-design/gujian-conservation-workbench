# 07 · 界面与交互形态

## 一、形态判断

产品采用工作台形态：左侧项目与任务，中间随任务切换的工作区，右侧常驻 AI 助手。用户在助手里说话，在工作区里看证据和改结果。

用户面对一个助手，服务端按任务路由模型。普通用户无需选择模型品牌，模型与供应商信息留在内部选型记录中。

三栏结构将对话、任务状态、数据和证据放在同一操作环境。用户可查看处理进度、定位依据，并在原图上修正结果。

结构依据见 [06 用户旅程](06_用户旅程.md) 的八项原型约束，重点满足自动推进、责任停靠、原图修正和分支并行。

交互参考 VS Code 和 Cursor 的工作台结构。中间工作对象为照片、构件数据和图纸，因此需支持图像框选和数据联动。

视觉形态、组件规格与状态表达见 [09 界面视觉规范](09_界面视觉规范.md)，本文只定义结构与交互。

全部视图采用左侧数据、右侧证据的结构。点击数据后，证据区跳到对应位置并高亮。

现状记录独立于构件清单，因为形制测绘与残损勘察分属两套标准体系：几何测绘依据 [CH/T 6005-2018《古建筑测绘规范》](https://std.samr.gov.cn/hb/search/stdHBDetailedCNF?id=8B1827F24F89BB19E05397BE0A0AB44A)，残损与结构安全依据 [GB/T 50165-2020《古建筑木结构维护与加固技术标准》](https://www.gongbiaoku.com/book/icz19014nxx)。两项工作可能由不同资质人员承担，责任边界不能合并。适用范围为木结构古建筑。

问题队列独立于图纸与检查：前者处理出图之前的数据问题，属 M3；后者处理出图之后的图面问题，属 M4。两类问题的处置时机和责任人不同。

图纸与检查在用户认知上是一个环节（旅程第六步出图和检查），因此定义为一个视图；工作台实现中按信息量分为图纸和检查两个页签，助手切换该视图时落到图纸页签并说明。

正式出图前需在图纸样式视图确认画法、标注规则和图签。

**表 5：助手消息类型**

## 五、五个关键交互

### 5.1 框选加一句话

框选修正对应用户旅程第四步。

流程：用户在中栏右半区的照片上拖出一个框，右栏输入区自动带上这个位置的引用，用户打字说明问题，发送。助手定位到对应构件或空白区域，执行修改，中栏数据同步更新并高亮变化处。

系统根据框选位置关联构件编号和表格行。

支持的说明方式见表 5。

**表 6：框选后可以说的话**

| 用户说 | 系统理解为 |
|---|---|
| 这里漏了一个雀替 | 在该位置新增构件，类型为雀替 |
| 将这个构件从雀替改为替木 | 修改该位置构件的类型 |
| 这个框位置不对，应该往左 | 调整位置框，重算相邻关系 |
| 这里没有构件 | 删除该条，记入本项目排除记录 |
| 这块被树挡住了，看不清 | 标记为不可见部位，进入待补拍清单 |

### 5.2 数据与证据双向联动

点击左半区任一条数据，右半区跳到对应证据并高亮。在右半区选中任一位置，左半区自动滚动到对应数据行。

这条规则覆盖全部工作区视图。点击图纸构件后，可查看原始照片、尺寸依据和修改记录。

### 5.3 停靠点

流程按状态自动推进，并在四类情况下停靠（见表 6）。

**表 7：四类停靠点**

| 停靠原因 | 例子 | 界面表现 |
|---|---|---|
| 证据不足 | 没有实测基准、关键部位被遮挡 | 右栏提问，左栏该步骤标为等待确认 |
| 结论存疑 | 铺作形制有两种可能、与旧图纸冲突 | 转为待办，存疑项在清单中置顶 |
| 规范选择 | 不可见部位如何在图上表达 | 右栏列出可选做法及各自后果 |
| 正式签发 | 成果交付前 | 只有责任人可以操作，其他角色不显示该按钮 |

停靠只影响相关分支。两处铺作存疑时，其余 45 个构件照常进入出图。

### 5.4 随时插话

用户可以在任何时刻打断当前流程，说明新的要求。例如识别进行到一半时说“先别管构件了，帮我看看资料够不够出侧立面”，助手暂停当前任务，切到资料视图回答，回答完询问是否继续。

切换任务时保留已完成结果和当前状态。

### 5.5 三种状态的可见区分

每一条数据都标明它的来源（见表 7）。

**表 8：数据状态**

| 状态 | 含义 | 建议表现 |
|---|---|---|
| 实测依据 | 有现场实测记录支持 | 实心标记，可点开查看原始记录 |
| AI 推测 | 由模型判断或按对称关系推算 | 空心标记，鼠标悬停显示推断依据 |
| 人工确认 | 经操作用户或责任人判断 | 带姓名标记，可点开查看理由 |

正式成果中的每条数据均需标明来源。无实测依据的尺寸需在图纸和交付说明中标注。

## 八、AI 动作清单

动作清单当前含 14 个已实现动作（第 1 代 6 个、第 2 代 7 个、第 3 代提前 1 个），另有 7 个第 3 代动作仅定义占位。模型经意图分发选中动作，参数校验失败回模型重试一次，二次失败落关键词匹配；停靠、退回和签发仍由固定流程与责任人控制。

通用约定（适用全部动作）：

1. 模型可见字段只有名称、描述、参数定义三项，确认级别、留痕方式等执行字段不进模型请求。
2. 参数进入执行后不可改写，留痕、界面展示与实际执行使用同一份参数。
3. 失败分级：参数不合规时将结构化错误回给模型重试一次，二次失败落关键词匹配，模型服务不可用直接走关键词；均不中断对话。清单外动作按未知动作返回。
4. 高成本动作（生成三维、生成图纸）执行前展示预计耗时与用量，执行中可取消，失败不自动重试。
5. 模型可见目录只投影已实现动作，环节切换不增删目录，不可用动作由前置条件拒绝并说明原因。

通用约定与下方确认规则借鉴 deepseek-harness 官方子系统文档（tools、approval、plan，2026-08 研读）；重试次数上限、关键词退路与预估展示为项目自定。

| 查询作业进度 | jobType（可选，默认全部活动作业） | 作业列表（阶段、已耗时、预估） | 无活动作业时如实说明 |
| 回答问题 | question（必填） | 回答加引用（构件、资料、位置） | 兜底动作无再退路 |
| 生成修改建议 | subjectRef（必填）、changeType（参数修改、类别修改、标记存疑、标记不可用、标记不可见、新增、删除）、payload（按类型定义） | 建议清单，每条含字段、原值、新值、依据、核对结论 | 参数不合规按通用分级；核对不通过仍出建议但附警示 |
| 框选修正 | bbox（必填）、instruction（必填） | 修正条目加相邻关系重算摘要 | 位置无法关联构件时向用户提问 |
| 重新识别 | scope（可选，默认当前视图对象集） | 识别结果集，命中与存疑分列 | 模型服务不可用提示稍后再试 |
| 推进流程 | 无 | 起止环节 | 前置不满足时结构化拒绝理由交模型组织说明 |
| 运行数据检查 | scope（可选，默认当前环节） | 检查项、结论、停靠事项结构化列表 | 按通用分级 |
| 生成三维模型 | note（可选备注） | 新版本号、实体数、耗时 | 作业失败结构化原因交模型组织说明，不自动重试 |
| 生成图纸 | views（可选，默认全套） | 图纸目录与版本关联 | 作业失败结构化原因交模型组织说明，不自动重试 |
| 导出成果 | format（格式枚举）、scope（范围） | 导出清单与哈希 | 前置不满足结构化拒绝 |

确认机制遵守四条规则：

1. 确认结果是封闭集合：允许一次、拒绝、用户撤回、通道不可用，除允许一次外全部按拒绝执行。确认界面未弹出、用户关闭页面、程序异常均不放行动作。
2. 一次确认只对当前一条生效，不存在本次同意后续默认同意的隐式升级。
3. 每次确认留两条成对记录：询问一条、决定一条，同一确认号关联。程序中断时留下有询问无决定的可检测状态。
4. 确认界面引用已展示的动作卡片，不另行复制参数副本。

浏览引导与写入控制分两层，互不读写：浏览环节的引导（该看什么、下一步去哪）是软性提示，不锁定任何动作、不留痕；写入、推进、签发是硬性确认层，走确认规则与留痕。环节切换不改变动作清单，动作可用性只由前置条件表达，不可用时拒绝并说明原因。

模型输出先经过字段白名单、编号检查、标准字段映射和合理性校验。数量、状态和来源由程序统计，模型负责组织说明。对话与按钮产生的修改使用同一套来源标记和历史记录。固定说法交给规则程序，表达多变且需要语义理解的任务交给模型。
