## 一句话结论

古建工作台下一步不应继续在固定数据和局部代码上增加功能。应先把真实输入、结构化数据、AI 处理、规则计算和人工确认串成可解释流程，再完成核心 PRD。PRD 确认后，使用模块化技术架构重构原型，并通过真实数据检验模型质量、成本和泛化能力。

## 1. 当前原型的主要缺口

当前原型已经呈现 AI 助手、业务步骤和人工确认，但演示仍依赖同一套固定数据，无法说明数据怎样进入系统、为什么需要这些字段，以及换一个项目后是否仍然成立。

导师在演示中重点追问了资料输入。当前数据来源和存放位置无法立即说明，暴露出三个问题：

1. 演示没有完整覆盖资料输入到成果交付。
2. 数据可能与页面或业务代码混在一起，难以替换和扩展。
3. 字段和样例主要由 AI 生成，JIAJIA 尚不能逐项解释设计依据。

作品集中的演示需要从真实输入开始。招聘方询问数据来源、字段含义和设计理由时，应能直接展示数据结构和对应产品判断。

## 2. 数据必须独立设计

数据应从页面和业务代码中独立出来。程序读取结构化数据生成页面和结果，不把项目样例写死在 HTML 或单个功能文件中。

近期可先使用独立 JSON 文件验证：

- 一个文件保存一个项目或一类项目数据。
- 系统支持选择或导入不同项目文件。
- 修改数据后，页面、检查和成果同步变化。
- 支持导出当前数据，便于复核和继续编辑。
- 图片等非文本资料通过文件路径、URL 或资源标识关联，不直接混入字段说明。

建筑、构件、位置、尺寸和子构件的嵌套结构只是导师现场示例，不是最终字段清单。正式字段应从产品输出和业务要求反推，并逐项说明：

| 需要说明 | 核心问题 |
|---|---|
| 字段含义 | 记录的对象或状态是什么 |
| 数据来源 | 来自任务书、实测、AI 推测、规则计算还是人工确认 |
| 使用位置 | 哪个环节、页面或成果使用该字段 |
| 是否必填 | 缺少后能否继续，能否形成正式成果 |
| 更新方式 | 谁能修改，修改后影响哪些结果 |

AI 可以协助生成结构和代码，但数据模型必须包含 JIAJIA 的产品判断。不能把“AI 生成了一套数据”当作设计依据。

## 3. 用不同数据验证泛化能力

结构化数据的价值不只是便于维护，还能检验产品是否只适用于当前样例。

至少准备两套存在明显差异的项目数据，验证：

1. 系统能否正确加载不同建筑和任务要求。
2. 页面和流程是否仍依赖高都玉皇庙的固定字段或文案。
3. AI 能否处理不同构件、资料缺口和成果要求。
4. 规则检查是否只对当前样例有效。
5. 修改一个模块的数据是否会误改其他模块。

模型估算值应与已知数据对照。验证重点是误差、失败条件和人工修改量，不是让模型生成一个看似合理的数字。

## 4. Agent 定义从加法转为减法

Agent 不需要堆叠大量细则。提示词过长会削弱重点，使不同要求的优先级趋同。确定性规则应写入程序，提示词只保留角色完成工作的核心要求。

一个 Agent 的基础定义可压缩为四部分：

1. **工作范围**：负责什么结果，不负责什么。
2. **工作原则**：通常按什么顺序判断和执行。
3. **验收标准**：完成后从产品、用户、开发等视角检查什么。
4. **禁止事项**：哪些情况必须确认，哪些行为不得执行。

专业工作能力不应拆成大量僵硬指令。可以参考同一垂直岗位的能力阶梯，提炼该角色应具备的判断能力。具体业务规则由脚本或规则文件执行。

不同工作场景的处理方法可拆成独立参考文件。Agent 先判断当前场景，再读取对应文件，避免把新品类探索、日常迭代、紧急问题和战略评估全部塞进同一提示词。

随着模型能力增强，Agent 定义会继续缩短。长期重点将从“反复定义角色”转为“准确提供项目背景、当前状态和任务约束”。

长对话中，项目上下文可能削弱角色要求。发现回答偏离职责时，可重新声明角色或新开对话，不能假设 Agent 会始终记住早期指令。

## 5. 模型选型需要商业计算

模型选型不是选择能力最强的模型，而是在合规和质量底线之上，选择成本可承担的方案。

建议按以下顺序判断：

1. **市场与合规**：确认服务地区、数据传输和部署方式是否符合隐私与数据要求。
2. **任务质量**：使用同一批真实任务测试模型能否达到最低可用标准。
3. **调用成本**：统计每次任务的 token、重试和人工修改成本。
4. **使用频率**：估算每位用户每天或每个项目的调用次数。
5. **产品收益**：估算付费、成本节省或品牌传播等收益。
6. **使用限制**：根据成本设置免费额度、调用次数和降级方案。

基础计算关系为：

`单位任务成本 × 任务次数 × 用户数量 = 预计模型成本`

再将模型成本与订阅收入、项目收入、人工节省和其他可说明的收益比较。估算不用于证明结果一定发生，而是为资源负责人提供是否继续投入的判断依据。

产品经理需要提出方案、成本和价值证据，但大额投入是否执行，应由掌握资源的人决定。相同方法也适用于功能和项目判断：先调查价值与投入，再决定接受、调整或拒绝需求。

## 6. PRD 先于技术架构

技术架构应在核心 PRD 明确后形成。需求、范围和验收条件仍在变化时，提前重构容易重复返工。

建议顺序为：

1. 完成并确认核心 PRD。
2. 将 PRD 交给 AI 架构角色分析。
3. 先输出技术架构方案，不直接写代码。
4. 使用另一个模型或角色交叉检查方案。
5. 确认方案后拆成可独立完成、可中断恢复的任务。
6. 按任务重构和测试。

产品经理不需要替开发决定全部技术细节，但应确认架构支持当前需求、后续扩展和维护。对外展示的原型也需要具备基本可维护性，不能长期依赖局部补丁。

## 7. 原型需要模块化

输入、数据、业务处理、对话、成果生成和检查应形成相对独立的模块，并通过明确接口交换数据。

模块化需要达到三个结果：

- 扩展输入类型时，不改动成果生成逻辑。
- 调整模型或提示词时，不破坏确定性检查规则。
- 修改一个业务模块时，其他模块不发生无关变化。

AI 编程时应先分析和规划，再执行代码修改。对于影响整体的调整，应要求 AI 从架构角度给出重构方案，不做连续的补丁式修改。

多 Agent 调度是导师展示其工作方法的案例，不代表古建产品必须做成多 Agent。是否拆分 Agent，应根据任务差异、模型效果、成本和用户理解成本决定。

## 8. 产品体验继续减少人工操作

对外展示的工作台需要更接近正式 toB 产品，并继续检查哪些人工操作可以删除或合并。

减少人工不等于取消专业责任。可以减少的是重复录入、资料整理、状态切换和低风险检查；实测、专业存疑判断和正式签发仍由对应人员负责。

每个需要人工介入的节点都应回答：

- 为什么系统不能继续处理。
- 用户需要补充什么信息或判断。
- 完成后哪些步骤自动继续。
- 如果用户不处理，成果受到什么限制。

## 9. 使用 AI 的前提是理解真实工作

有效使用 AI 的前提是掌握真实工作流、角色分工和决策方式。AI 只是提高执行效率，不能代替产品经理定义业务、数据和验收标准。

JIAJIA 需要能解释：

- 真实项目原来怎样完成。
- 哪些步骤需要理解，哪些步骤结果唯一。
- 哪些决定涉及专业责任。
- AI、规则程序和人工如何交换结果。
- 失败时怎样降级和恢复。

只有先理解这些内容，才能把真实工作方法转成 Agent 的工作范围、规则模块和检查标准。

## 10. 简历与求职建议

简历需要先用一句话说明跨领域背景，再展开具体能力。可围绕“空间设计背景与 AI 产品实践的交叉经验”组织，但最终表述必须由真实经历支持。

教育经历下增加一句与目标岗位的关联说明，解释研究生学习、项目训练怎样支持产品工作。不要只罗列课程和项目名称。

求职阶段应尽快获得真实面试反馈。可先投递接受意愿较低的小型公司，降低心理压力，用实际面试检验简历表达和问答准备，再逐步投递更优先的岗位。

简历和作品集中的每句话都必须可解释。需要准备对应的数据来源、个人决策、所做工作、结果证据和能力边界，不能用“AI 帮我生成”替代个人贡献。
