条件在开工前写定，逐条可判定。做不到即为未完成，不以能跑通或已接线代替。

## 一、验收条件

| 序 | 条件 | 结果 |
|---:|---|---|
| 1 | 四个动作在登记表中状态为 `executable`，界面文档表 12 同步标注状态，`action-catalog.test.ts` 通过 | |
| 2 | 退回重做：说一句退回某项，先看到受影响范围，确认后写入退回记录，含理由、退回人、时间、目标环节、影响范围 | |
| 3 | 退回后受影响成果标为失效，无关成果保持有效（F17 验收标准） | |
| 4 | 变更任务参数：说换比例或加立面，先看到受影响成果清单，确认后任务书追加一版，旧版仍在 | |
| 5 | 设置图纸样式：说改画法或版面，逐条确认后写入，已生成的受影响图纸标为失效（F12 验收标准） | |
| 6 | 存入构件库：责任人确认后写入词表条目，条目带确认人与时间 | |

| 8 | 四个动作的留痕都出现在修改历史页面，含时间、操作人、对象、理由 | |
| 9 | 影响范围由程序计算，不取自模型输出。有测试证明模型给出的影响范围不被采信 | |
| 10 | 分发用例集补四个动作各三条，`dispatch.test.ts` 的覆盖断言通过，四个动作实际派发命中并回填用例集第 3 节 | |
| 11 | `node .claude/skills/quality-check/scripts/run-all.mjs --full` 必须修复项为 0 | |
| 12 | 演示矩阵二十一格仍全满 | |

## 二、判定说明

第 3 与第 5 条是这批里最容易做成假通过的两条。写一条记录说某某已失效很容易，让检查与出图链路真的据此拒绝才算数。判定时要看的是资格判定或检查结果发生变化，不是多了一行状态字段。

第 7 条不能用当前操作人顶替。演示环境里操作人是本机随机 id，多半不在责任人清单里，因此这条的预期结果是被拒。被拒是正确行为，不是缺陷。

第 9 条针对同一类失效模式：模型看不到的东西不能由模型给。框选修正那次是坐标，这次是影响范围。影响范围要遍历依赖边算出来，模型没有这份数据。

第 10 条不可跳过。四个动作转为 `executable` 时，`dispatch.test.ts` 的覆盖断言会强制要求每个动作至少三条用例。
