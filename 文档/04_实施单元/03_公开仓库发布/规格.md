# 公开仓库发布 · 规格

## 一、依据

技术架构 12.3 Git 与公开仓库、12.4 大产物与 Git 对象。核心 PRD 第 2.5 节的阶段定义。

不新设需求。本单元不改产品功能，只把当前状态发布到公开仓库。

## 二、范围

把实施分支 `codex/professional-workbench-rebuild` 的当前工作区状态发布到 `jiajiajiang91-design/gujian-conservation-workbench` 的 `main`，采用当前状态替换，不整合两套无关历史。

六个步骤按 12.3 原文，顺序不变：

1. 远端建只读备份分支 `archive/portfolio-v0.0` 与标签 `portfolio/v0.0`，两者精确指向 `ac6abbc`。先于任何写操作。
2. 瘦身当前工作区。
3. 扫描当前跟踪的全部文件。只扫工作区状态，不扫历史提交。
4. 用当前状态建立全新的初始提交替换 `main`，不携带实施分支的历史。
5. 发布后在 README 写明开发周期与关键节点。
6. 回退通过备份分支恢复。

## 三、口径

**替换而非整合。** 理由见 12.3：实施分支 167 个提交的历史中包含早期的 `.env` 引用与大对象，公开后无法撤回。整合方案的完整流程保留在历史归档，需要保留过程历史时再启用。

**第 1 步与第 4 步是对外动作，各自单独确认。** 第 1 步向公开远端写分支与标签，第 4 步不可逆。两步都不在未确认的情况下执行。

**扫描口径是暴露面而不是内容质量。** 扫描判定的是公开后是否泄露不该泄露的东西、许可是否说清楚，不判定文档写得好不好。

**发布内容以当前工作区为准。** 不为发布另做一个精简版本，也不在发布前临时改产品结论。

## 四、不做什么

- 不重写历史，不用 filter-branch 或类似手段清理旧提交。
- 不删除远端已有内容，`ac6abbc` 由备份分支与标签固定。
- 不为压体量而删除产物文件却保留其清单，那会让演示矩阵显示有内容而实际打不开。
- 不改演示项目定义，除非你就体量取舍另行决定。
- 不建 GitHub Release，不上传大产物到 Release。12.4 允许这条路，本单元不走。
