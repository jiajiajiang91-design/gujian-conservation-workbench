# 公开仓库发布方案

> 本节原为技术架构 12.3，2026-08-21 随发布完成移入本单元。

## 一、方案

实施分支为 `codex/professional-workbench-rebuild`。本地 HEAD 与 `origin/main` 没有共同祖先，远端 `ac6abbc` 是 2026-08-12 发布的作品集版本，77 个文件。

远端为 `jiajiajiang91-design/gujian-conservation-workbench`。发布采用当前状态替换，不整合两套无关历史：

1. 远端建只读备份分支 `archive/portfolio-v0.0` 与标签 `portfolio/v0.0`，两者精确指向 `ac6abbc`。这一步保证旧版本可回退，先于任何写操作执行。
2. 瘦身当前工作区。单文件不超过 45 MB。跟踪总量目标 100 MB 以内。

   目标由 50 MB 改为 100 MB（2026-08-21）。50 MB 没有出处，而按它压体量要付实际代价：演示包不能只删产物文件而留清单，演示矩阵读的是包内清单不读产物，那样会显示有 23 项而点开报错；上游可变字体是字体闭包校验按 sha256 核对的对象，删了克隆者跑不了这项校验；运行时字体裁剪会在未登记的汉字上出空白并撞制图合同校验。当前跟踪总量 93.6 MB，单文件最大 30 MB，GitHub 的实际约束是单文件 100 MB、仓库 1 GB 建议值，均在内。测量与三条路的取舍见 `文档/05_验证证据/13_发布前扫描/发布前扫描报告.md` 第四节。
3. 扫描当前跟踪的全部文件，逐项检查密钥、用户名、绝对路径、私有资料、许可、外部 DWG、大对象和过期资格表述。只扫工作区状态，不扫历史提交。
4. 用当前状态建立全新的初始提交替换 `main`，不携带实施分支的历史。
5. 发布后在 README 写明开发周期与关键节点，替代提交历史承担的时间线说明。
6. 回退通过备份分支恢复，不依赖历史重写。

选择替换而非整合的理由：实施分支 167 个提交的历史中包含早期的 `.env` 引用与大对象，公开后无法撤回；作品集场景下干净的当前状态比完整的过程历史更有价值。整合方案的完整流程保留在 `文档/99_历史归档/`，需要保留过程历史时再启用。

每个实施任务仍使用独立提交。功能回退使用 `git revert`，不通过删除数据完成。

### 12.4 大产物与 Git 对象

Git 只跟踪源码、合同、测试、许可、小型哈希摘要和必要缩略图。可重复生成的 DXF、SVG、PNG、GLB、压缩 Drawing IR 和来源 sidecar 进入忽略目录；需要公开下载时进入 GitHub Release，并附 manifest、SHA-256、生成提交和工具版本。

`.gitignore` 对已经跟踪的文件无效。现有历史中的大对象不通过历史重写删除，但新的 public integration 分支不得因此自动带入旧大对象。拟继续跟踪的大文件必须逐项说明无法重建的原因、许可和容量影响。
