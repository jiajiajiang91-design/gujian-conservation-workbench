# 古建保护成果工作台

把古建保护项目的一次现场记录，变成一套能追到出处的测绘成果。

资料入库后，系统识别尺寸与构件，由人逐条确认。确认后的数据驱动三维模型、平立剖图纸、成果检查与交付包的生成。每一个数字都能点回它的来源：哪张照片、哪次实测、谁在什么时候确认的。

**这是作品集项目，不是可用于实际工程的软件。** 产出的图纸与模型标记为代理成果、未签发、未达专业样板等级，不构成专业结论。

## 解决的问题

这套工具把实测值、推算值和形制经验值在数据结构里分开。这种区分贯穿到图面与交付包。

古建测绘的成果里，这三类数值通常混在一起。图纸交付之后，无法确认某个数值是实测得到还是推算得到。

因此有两条硬规则：

- 不合格的尺寸进不了正式成果。系统宁可阻断，也不补默认值。
- 推算值始终显示为推算值。规则给出的应然值不能当作实测依据。

## 当前能力

三个演示项目在首次打开时自动装载，每个都走完七步：任务卡、资料清单、实测基准、构件清单、三维模型、图纸与检查、交付包。

| 演示项目 | 资料 | 构件 | 说明 |
|---|---|---|---|
| 团队构造样板 | 2 份 | 1258 个 | 局部构造样板，验证几何与制图管线 |
| Dai Loy 赌馆博物馆 | 7 份 | 75 个 | 美国 HABS 公开实测图，验证完整工程流程 |
| 高都玉皇庙主殿 | 3 份 | 1131 个 | 中国官式木构，只有照片，尺寸由形制规则推算 |

助手层有 14 个受控动作，覆盖切换视图、生成图纸、在照片上框选修正构件等操作。动作的实现状态由代码登记表派生，两侧各有测试保证一致，文档无法单方面宣称已交付。

## 产品定义

三种数据来源的区分是这个产品的核心判断，其余设计都从它派生。实测值、规则推算值与模型识别值分开存储、分开标注，任何一处都不允许把推算显示为实测。

由此定下三条口径：

- **需求来源唯一。** 产品范围以 PRD 为准。先改文档再改实现，不从实现反向补文档。
- **人工只保留三类责任。** 补充系统取不到的现场事实、选择没有唯一答案的专业方案、审核成组成果并签发。其余环节不设固定确认。
- **演示不靠阻断体现严谨。** 三个演示项目全程跑通，用来源标记表达数据性质，阻断只发生在正式签发。

## 工作方式

`.claude` 目录定义了推进这个项目的角色、流程与检查，它与代码同为项目产出。

- **六个角色与六个技能包。** 角色为项目负责人、产品经理、调研、古建审阅、文档、架构。技能包为写 PRD、产品判断、外部调研、技术架构、写实施单元、质量检查。角色定义只写职责与红线，方法按场景读技能包。
- **一个实施单元三份文件。** 规格写做什么，计划按组分步且每组自带验证，验收条件在开工前写定。做不到即为未完成，不以能跑通代替。
- **机器能判定的规则交给脚本。** `.claude/skills/quality-check` 检查文档字符规范、跨文档与文档代码之间的引用、实施单元与路线图的状态一致性。文档声称已交付而代码未实现时，测试会失败。

完整定义见 [协作体系](.claude/context/协作体系.md)。

## 本地运行

需要 Node 20.19 以上、pnpm 11.16，仓库用 corepack 锁定版本。CAD worker 使用 Python 3.12 与 CadQuery 2.8，依赖与哈希锁在 `workers/cad/requirements.lock`。

```bash
corepack pnpm install
```

`交互原型/02_AI工作台` 是早期原型，不在 pnpm workspace 内，有自己的锁文件，回归测试仍在运行它。安装它的依赖：

```bash
corepack pnpm run install:legacy
```

两步装完后运行全量检查：

```bash
corepack pnpm check
```

启动开发环境：

```bash
corepack pnpm dev
```

工作台在 `http://127.0.0.1:5173`，服务端在 `8787`。

模型识别功能需要在 `apps/server/.env` 配置密钥，配置项见 `apps/server/.env.example`。不配置时其余功能照常运行，识别相关按钮显示为不可用。

## 边界

- 演示数据标为示例来源，不能作为真实成果。
- 高都项目没有实测记录，全部尺寸由形制规则推算并在图上标注，可生成代理成果但不具备正式资格。
- 模型识别的结果先进候选区，人工确认后才写入项目。
- 未实现按图纸自动出具专业结论，也不替代真实项目负责人的审核签发。
