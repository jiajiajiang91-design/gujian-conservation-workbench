## 打开方式

双击 `index.html` 只能看演示数据。真实调用必须由项目自带的后端启动：

```powershell
cd 交互原型\02_AI工作台
Copy-Item .env.example .env
# 在 .env 的 MOONSHOT_API_KEY 后填写测试密钥
npm start
```

然后浏览器打开 `http://127.0.0.1:8795/`。

改过代码后如果页面没变化，按 Ctrl+Shift+R 硬刷新，浏览器会缓存旧的 js。

## API 与访问限制

密钥只由本地后端或部署平台的环境变量读取。浏览器设置页不保存、不显示密钥，也不会把密钥发给访客。`.env` 已被 Git 忽略，不能改成其他文件名后提交。

默认限制为每位访客每分钟 6 次、每天 80 次，全站每天 300 次；单次请求不超过 6MB、8000 token。后端还会检查来源、任务类型、消息结构和服务端模型路由。限制可在 `.env` 调整。

**后端未配置时主流程不调用模型**，所有结果标为「演示数据」，顶部显示演示模式。这种状态下看到的是预置内容，不代表模型能力。

## AI 做什么，程序做什么

这一节回答「AI 在哪里」，也说明哪些事**不是** AI 做的。

**真实调用模型的步骤**（后端服务可用时，每次调用的耗时和 token 都记在设置页）：

| 步骤 | 模型做什么 | 纯程序能不能做 |
|---|---|---|
| 立项理解 | 从你第一句话里提取对象、地点、成果类型、比例、工期，判断本机有没有这个项目的资料 | 不能。这是自由文本 |
| 读任务书 | 从任务书正文提取成果、精度、规范、交付要求，并标出各自出自第几条 | 不能。任务书是自由格式中文 |
| 资料判断 | 判断现有资料够不够出这张图，缺什么、不补的后果是什么 | 不能。要理解资料内容与成果要求的关系 |
| 草图解析 | 从手写尺寸记录里读出数值并判断各是哪个部位，说不准的如实标出来 | 不能 |
| 资料分类 | 判断上传图片是现场照片、草图、任务书还是已有图纸 | 只能按扩展名判断，不能理解画面 |
| 图片文字提取 | 从任务书截图或手写草图中提取要求和尺寸 | 不能稳定处理版面、手写和模糊内容 |
| 构件识别 | 从照片认出构件、材料、位置框 | 不能。这是全流程价值最高的一步 |
| 检查解释 | 把规则程序报出的问题翻译成人能懂的说明并指到位置 | 不能 |
| 修改建议 | 找出与实测矛盾的数据，给出可一键应用的结构化改法 | 不能 |
| 交付说明 | 按当前数据起草限制条件，指到具体部位和构件 | 不能 |
| 意图分发 | 判断你说的话是要跳转、修改、继续、重识别还是提问，选择对应动作 | 关键词只能覆盖固定说法，换个说法就失灵。分发失败时退回关键词匹配 |
| 自由问答 | 基于工作区完整数据回答你的追问 | 不能 |

**由规则程序做的**（不用模型，结果唯一可复算）：尺寸换算、开间之和与通面阔的核对、几何关系校验、出图、标注碰撞检测、规范符合性检查、交付包组合、修改建议的合理性复核。

**流程闸门由确定性状态机控制，对话意图由模型分发。** 两层分开：什么时候停下来问人、存疑没清能不能往下走、签发归谁，这些闸门由 `orchestrator.js` 的固定逻辑决定，模型绕不过去；而你在对话里说的话对应哪个动作（跳转、修改、继续、重识别、提问），由模型按一张受控动作清单判断，判断失败退回关键词匹配。动作清单之外的事助手做不了，每个动作执行前仍走字段白名单和合理性校验。这是有意的：正式业务里流程闸门要可预测、可审计，但听懂人话这件事关键词做不到。

**视图浏览不设锁。** 任何环节的页面随时可以点开看，没走到的步骤显示初始内容并提示。停靠点管的是写入和推进，不是不让看。

**框选修正是混合的。** 你在照片上框一块说「这里漏了一个雀替」，其中构件名称的提取、对称构件的查找、类别推断由本地规则和受控词表完成，不调模型；模型只在你说的话超出这些规则时才介入。这样做是因为规则稳定、零延迟、零成本。界面上会说明这一次是规则处理还是模型处理。

## 用自己的资料测试

把文件直接拖进对话框，助手会先判断这是什么，再分别处理，结果**写进业务数据并推动流程**，不是识别完报个数字就完了。

| 拖进什么 | 会发生什么 |
|---|---|
| 现场照片 | 识别构件，替换构件清单，主图换成你这张，存疑项由模型按实际遮挡情况提出，视图跳到构件清单 |
| 手写尺寸草图照片 | 从纸上读出数值和部位，写进实测表替换演示数据，没标部位的留给你指认，视图跳到实测基准 |
| 任务书照片或截图 | 提取成果、比例、规范、精度、交付要求，填进任务卡并标出各自出自第几条，视图跳到任务卡 |

一次实测：拖入一张东呈古佛堂的现场照片，模型先判断出这是立面照片并指出「右侧树木枝叶遮挡部分屋檐和墙体；人物出现在画面左侧边缘造成一定遮挡」，然后识别出 23 个构件，存疑项包括「金柱是否存在：因室内黑暗且板门半开，无法判断室内是否有金柱及内槽结构」。这些都是看着那张照片说的，换一张照片结论就不同。

**不支持的格式会明确说明原因和替代办法**：PDF 需要转成图片或拍照，Word 需要另存后截图，DWG 是二进制格式浏览器读不了，DXF 的解析和导出下一轮做。

## 新建项目不继承演示数据

说一个本机没有的项目时，任务卡会**清空后重建**，只有模型从你话里提取到的字段有值，其余标为「待确认」。

实测：说「给上海外滩某历史建筑做一套屋顶测绘图，1:100」，任务卡里只有成果类型和比例标了 ai，规范、交付格式、附带材料、工期、精度要求全部是「待确认」，不会留着高都玉皇庙的内容。此前这里会把两个项目的信息混在一张卡上，来源标签也救不了。

## 每条数据都标来源

七种来源，界面上用不同徽章区分，顶部还有汇总：

| 标记 | 含义 |
|---|---|
| 演示数据 | 原型预置，未调用模型。虚线边框，一眼可辨 |
| AI 实时 | 本次真实调用模型生成 |
| 程序计算 | 规则程序算出，结果唯一可复算 |
| 实测依据 | 有现场实测记录支持 |
| 人工确认 | 由项目人员判定并署名 |
| 待确认 | 证据不足，尚未判定 |
| 缺失 | 所需资料不存在 |

此前所有预置内容都标成「AI 推测」，助手还会说「我看了文件夹」，用户根本无法判断这到底是不是模型做的，AI 的可靠性也就无从验证。现在预置一律标 demo，只有真的调用过才改标 ai。

## 效率与成本记账

“服务与数据”按任务和模型记录输入、输出、缓存、耗时、重试、费用、采用方式、失败和降级。费用只使用带官方来源和核对日期的服务端价格；未配置价格的调用显示“待配置”。

设置页还可以录入同一任务的人工独立时间和 AI 后核对修改时间。单次成功任务应比较 API、失败重试和人工修改成本，不能再用统一 Token 单价代替。

**但这不等于「AI 提升了效率」。** 缺的是人工基线：同一份任务，人读任务书要多久、整理构件要多久、AI 首次识别有多少项被直接采用。这些只能在真实项目里测，13-3 第五节列的指标目前一条都没有真实数据。所以效率提升仍是产品假设，不是已经证明的结果。

## 演示流程

把这句话粘贴进右下输入框发送：

> 给山西高平高都玉皇庙主殿做一套正立面现状测绘图，1:50，甲方要求两周内交。资料在 D 盘 gaodu 文件夹里，有现场照片和一份委托任务书，去年的平面图也在里面。

之后按助手的提问往下走。八个步骤依次是建立任务、整理资料、核对实测、核对构件、记录现状、图纸样式、出图与检查、交付归档。

**核心交互在核对构件这一步**：在右边照片上按住拖动画一个框，松开后直接在输入框说「这里漏了一个雀替」，助手会定位、补录、按对称关系推算尺寸，并记入修改历史。

其他可以试的说法：

| 说什么 | 会发生什么 |
|---|---|
| 这个不是雀替，是替木 | 改正类别，保留原判断记录 |
| 这里根本没有构件 | 删除并记入本项目排除记录 |
| 这块被树挡住了 | 标为不可见部位，进补拍清单 |
| 把不合理的尺寸都改正确 | 生成可一键应用的修改建议，见下 |
| 去看资料 / 打开构件 | 跳到对应视图 |
| 任意问题 | AI 服务可用时走真实模型回答 |

## AI 提议，你确认

说「把不合理的尺寸都改正确」这类话时，助手不只是给一段文字，而是逐条给出可以直接点的修改卡片：

```
P03 檐柱  尺寸
高 3950mm，宽 380mm（估）  →  高 3950mm，宽 380mm
P03 的宽度 380mm 与实测记录中的柱宽一致，无需估计。
[应用]  [忽略]
```

每条可以单独应用或忽略，下方有「全部应用」。应用后数据立即更新，构件状态从 AI 推测变为人工确认，并写入修改历史，能查到理由、操作人和时间；忽略也会留痕，记为人工判断不采纳。

可以改的不只是构件。实测记录的部位和数值、现状记录的内容和依据都能改，卡片上会标出对象类型。

**为什么不做成自动改**。实测里模型提的建议常有错，而且它自己标的把握并不可信：

- 建议把踏步宽 2000mm 改成 4200mm，理由是「踏步尺寸应与明间面阔一致」，标把握高。理由不成立。
- 建议把屋面檐口高从 5200mm 改成 1200mm，理由是「实测记录中的待确认 3：1200mm」，也标把握高。檐柱实测就有 3950mm，檐口高 1200mm 几何上不可能。

如果一句话自动改完，这些错误直接进正式成果，而且没人知道是怎么进去的。

**三道防线**。模型只返回结构化指令，不直接写数据：

1. 字段白名单、编号存在性、新旧值相同的建议全部丢弃，并告诉你丢了几条。
2. `js/editcheck.js` 逐条做合理性核对：数值变化幅度、檐口高与檐柱高的几何关系、台基高上限、去掉估算标记但实测里没这个数、数值与某项实测同数但部位对不上。命中的条目会红底标出，并写明程序核对发现了什么。
3. 按钮分成两个：「应用无疑问的 N 条」和「全部应用」，有疑问的默认不批量应用。应用一条后，同批次剩余条目会重算警告，因为数据已经变了。

上面那条檐口高 1200mm 的建议，程序一次抓出三个问题：数值缩小到原来的 23%、几何上不成立、去掉估算标记但实测里没这个数。这就是把确定性计算交给程序、把判断留给人的实际效果。

## 关于识别数据

默认使用本地已验证的识别结果，来自 `../../验证材料/02_PoC工作流验证/部件识别_高都玉皇庙正立面.json` 的真实盲测结论，位置框为对照原照片人工标注。

**修正会被记住。** 专业人员确认过的形制判断进构件库，人工判定不存在的误识别进排除记录，两者在每次真实识别时回传给模型：已确认的按结论处理，已排除的不再提出。对识别结果有疑问时直接说，例如「P11 是不是认错了，重新看一下」，会触发一次带着这个疑问的真实识别，即使识别数据源设为本地。

在“服务与数据”中可以切换示例结果和在线处理。普通用户不选择模型，任务路由由服务端控制。

## 模型接入与任务路由

浏览器只提交 `task_id` 和业务输入，不提交模型名称、推理参数或密钥。服务端依次执行：

`任务协议 → 任务路由 → 模型注册 → 供应商适配 → 统一结果与度量`

当前调用点归为指令路由、文本结构化、文档视觉理解、专业视觉识别、说明生成和综合分析六类。默认仍使用 Moonshot V1 128K 处理文字任务、Kimi K2.6 处理视觉任务，以保持现有演示效果；这只是当前路由，不是最终选型结论。

OpenAI Chat Completions 兼容供应商通过 `.env` 中的 `AI_PROVIDERS_JSON`、`AI_MODELS_JSON` 和 `AI_TASK_ROUTES_JSON` 接入。参数差异写在模型声明或供应商适配器中，业务代码不再按模型名称判断。

模型选型使用固定古建样本。先检查字段准确、缺失不补猜、构件可定位等质量底线；通过后再比较耗时、输入输出费用、失败重试和人工修改时间。2026-08-06 的单图测试只保留为早期观察，不能证明某模型是均衡最优解。

## 为什么尺寸核对交给程序而不是模型

上面那张对话测试表就是答案：三个模型两种结论，快的那个还算错并编造了一条不存在的矛盾。同一份数据换个模型结论就变，这种结果不能进正式成果。

矛盾本身是客观存在的：明间 4200 + 次间 3600 × 2 = 11400，实测通面阔 15800，差 4400mm，远超任务书 ±20mm 的精度要求。

所以这类核对写成了规则程序（`js/datumcheck.js`），三条规则：各间面阔之和与通面阔一致、檐柱高大于台基高、明间不小于次间。程序算出来的结果唯一、可复算、不会因为换个模型就变。助手只负责把结果讲清楚，并说明这是程序算的不是它判断的。

这是 13-2 里“AI 负责看和说，规则负责算和管”那条分工在原型里的具体落点。

即使用可用的那个模型，也有两个已知问题：

一是**位置框不可靠**。返回的坐标是规整数值，多个构件共用相同边界，看得出是按典型布局推测而非真实定位。

二是**内容会出现幻觉**。高都玉皇庙主殿的前廊是完全敞开的，无槛墙无门窗，模型却给出了板门、直棂窗和隔扇，套用了常见三开间殿的构成。

所以真实调用适合演示链路，不能拿它的结果当识别精度。这也印证了产品里三种状态标记的必要性：AI 推测的东西必须让人一眼看出来是推测。

编排层是这套形态的关键，传统后台没有这一层。流程仍由 `orchestrator.js` 负责；项目业务数据只改 `data/projects/*.json`，加载和 schema 规则才改 `js/data.js`。

## 项目数据、切换与往返

当前内置两个真正可打开的独立项目：高都玉皇庙主殿和东呈古佛堂正殿。两者的构件系统、照片、尺寸关系和交付限制不同；东呈按五开间关系配置，不再复用高都的三开间公式。

项目总览支持：

- 选择任一内置或已导入项目；切换后图片、任务、构件和状态一起变化。
- 导入本地 JSON。导入前检查 schema、字段类型、数量、ID、构件位置框、来源枚举和资源路径；同 ID 自动保存为带 `originProjectId` 的副本。
- 导出当前结构化工作包。导出包分为原始证据、当前业务、工作流和审计记录，不包含消息、当前选中项、模型密钥或图片二进制。
- 每个项目使用 `gujian-wt-state:<projectId>` 独立存档。旧 `gujian-wt-state` 只复制迁移，原键保留用于回退。

JSON 只保证结构化数据往返。图片不会嵌入其中，资源只允许引用工作台 `assets/` 目录下的安全文件名；不加载导入数据提供的远程 URL。

高都和东呈当前都标记为 `demo-proxy`，用于 V1A 代理验证，不得对外正式交付。高都的 5 项控制尺寸转写没有原始纸本进入原型，因此来源统一为 `demo`，不会伪装成 `measured`。

## 两条路都能走：点按钮，或者说话

每个视图底部都有操作条，主按钮直接写下一步做什么，和旧版 23 屏原型一样：

| 视图 | 主按钮 | 其他 |
|---|---|---|
| 项目列表 | 点任一项目卡片进入 | 导入 / 导出项目 JSON、新建测绘任务 |
| 任务卡 | 任务卡没问题，去整理资料 | 我要传实测记录 / 先出草图 |
| 资料清单 | 资料够用，去核对实测 | 标记需要补拍 / 回任务卡 |
| 实测基准 | 基准已建立，开始识别构件 | 跳过按估算出图 / 回资料清单 |
| 构件清单 | 构件核对完，去记录现状 | 处理下一项存疑 / 重新识别 |
| 现状记录 | 现状记录无误，去定图纸样式 | 标记待现场复查 |
| 图纸样式 | 样式定了，开始出图 | 回记录现状 |
| 图纸与检查 | 检查通过，去组交付包 | 重新出图 / 回构件清单 / 退回上一环节 |
| 交付包 | 导出交付包 | 接收方退回 / 回图纸与检查 |

还有待办没处理时主按钮会置灰并写明还差几项，比如「还有 4 项存疑要判定」。

代理验证可以只点按钮走完整流程；只有取得真实任务范围、实测证据、未决项处理、当前版正式图和责任签发后，正式交付入口才会开放。对话是随时可用的另一条路，不是唯一的路。

## 图纸有两个视图，不是二选一

之前我犯了个错：为了证明数据驱动，把 poc 里参数化脚本真实跑出来的专业图换成了自己画的 SVG 方块，结果比原来更不可信。

现在证据区有两个标签：

- **既有成果预览**：poc 参数化脚本输出的 DXF 渲染 PNG，只证明专业表达方向，不会伪装成随当前数据实时更新。
- **数据校核图**：按当前构件数据实时画的 SVG，用来核对数据是否齐全、改动有没有生效。

既有预览记录项目 ID、生成版本、生成时间、参数摘要和 `preview/current/stale` 状态。任务、尺寸、构件、现状或样式变化后自动标为 `stale`；校核图则按当前数据实时更新。

## 草图水印

无实测基准、代理验证项目、仍有未决项、检查尚未运行或正式图不是 `current` 时，图纸会显示草图/代理边界，正式交付按钮置灰并写明原因。结构化工作包仍可导出，用于恢复和继续工作。

## 退回处理

图纸和交付两处都有「退回上一环节」。点了之后先问退回原因属于哪一类，然后只把对应环节及其之后的步骤重置，前面已确认的保留：

| 退回原因 | 回到哪 | 保留什么 |
|---|---|---|
| 某个构件认错了或漏了 | 构件清单 | 任务、资料、实测全部保留 |
| 某项尺寸不对 | 实测基准 | 任务、资料保留，构件识别结果保留 |
| 图纸表达不符合规范 | 图纸样式 | 对象数据全部不动 |
| 资料不全需要补拍 | 资料清单 | 任务卡保留 |

退回原因、处理人和时间进责任记录。实测验证：从交付退回构件清单后，前三个环节仍为已完成，只有构件环节变成待处理。

## 图纸和检查都由数据实时生成

既有 PNG 与实时 SVG 现在明确分工；规则检查按当前数据运行。浏览静态预览不等于检查完成，只有点击重新生成与检查后才记录 `检查已运行`，业务数据变化会让该状态再次失效。

现在改成真的：

**图纸**（`js/drawgen.js`）。按当前构件数据实时画 SVG。屋面画成带瓦垄的梯形、柱带柱础和柱身线、斗栱按开间画密排小格、台基和踏步画成阶梯、雀替画成带弧的托、脊饰画在脊线上。尺寸链从实测记录取值，没有实测的标“按图估算”。图签里的构件数、估算数、签发人都从数据来。环境陈设默认不画，按规范环境物不入立面主体，需要时可以勾选显示。

实测验证：删掉一根檐柱并把一个构件标为不可见，SVG 图元从 280 变成 273，检查项从 5 条变成 6 条，多出来的正是“1 处为不可见部位”。

**检查**（`js/checkrules.js`）。九类规则按当前数据实时算：图签字段、标注碰撞（用构件位置框重叠面积判断）、推测值进图、不可见部位、未处理的存疑项、材料无检测依据、缺尺寸的构件、实测数据矛盾、责任人未指定。分成能自动修的和必须人决定的两类。

**要说清楚的边界**：实时 SVG 是数据校核图，不是符合规范的正式测绘图；静态 PNG 是既有成果预览，也不是当前数据的实时产物。真正的数据驱动 CAD/DXF 参数化画法规则库仍是后续独立任务。

## 这一轮修掉的问题

全流程回归后修的，记下来避免重复踩：

| 问题 | 原因 | 处理 |
|---|---|---|
| 真实识别报「图片读取失败」 | 同源图片设了 `crossOrigin="anonymous"`，浏览器就要求服务器返回 CORS 头，而 python http.server 不返回 | 只对跨域图片设该属性 |
| 反复切换视图后越来越卡 | 视图里用全局 `Store.sub` 订阅，视图重建一次就多一个回调，永不释放 | 新增视图级订阅 `subView`，切视图时清空 |
| 说「帮我推测数值」只回文字 | 意图识别只认「改正确」这类词 | 扩到推测、填上、补全、你来定等，并排除疑问句 |
| 助手给了具体数值却没法应用 | 只有显式要求修改时才生成指令 | 回答里出现可落地的值时，主动追问要不要写进数据 |
| 建议只能改构件 | 应用逻辑写死在构件上 | 支持构件、实测、现状三类对象 |
| 服务端 429 直接失败 | 没有重试 | 429/5xx 按 2、5、9 秒退避重试，界面显示第几次重试 |
| 框选后切视图，引用还在 | 切视图没清引用，下一句话会被当成对旧位置的修正 | 切视图时清除引用 |
| 交付完成后状态条仍显示「等你签发」 | 三级确认完成没更新状态条 | 补上 |
| 模型把字段写成 `尺寸\|数据来源` | 直接当字段名用会写进不存在的属性 | 按分隔符拆开取第一个合法字段 |
| 判断理由弹窗点取消也当成确认 | 原生 `prompt` 取消时返回 `null`，代码没判断就继续写入判定 | 六处原生弹窗全部换成应用内弹层，取消时明确中止；理由必填，弹层里能看到正在给哪一项写、判断人是谁 |
| 点「先看演示流程」后卡在建立任务不动 | 新增的 no-service、no-project 卡片只画了选项，没写回调 | 补上两个分支的处理；AI 服务不可用时仍有完整演示路径 |
| 立项理解报 `Cannot access 是本机项目 before initialization` | 我改代码时把变量引用写在了声明之前 | 调整声明顺序 |
| 上传图片只报个构件数，不进业务链 | onDrop 识别完就结束了，没写回数据也没推动流程 | 先分类再分别处理，结果写进构件清单、实测表或任务卡，并跳到对应视图 |
| 新建项目继承了演示项目的字段 | 只覆盖模型提取到的字段，其余保留原值 | 非本机项目时任务卡清空重建，未提取到的标「待确认」 |
| 资料清单点了行，底部按钮消失 | `paint()` 重写 `innerHTML`，把操作条一起冲掉了 | 内容区拆成 `pane-body`，操作条挂外层，八个视图统一改造 |

## 已知未做

- 两个内置项目都只用于代理验证，没有一套带可核查原始实测证据的数据可以通过正式交付门槛
- 正式 DWG/DXF 的数据驱动画法规则库没做；当前使用既有脚本输出的 PNG 预览和实时 SVG 校核图
- JSON 不嵌入图片；完整项目包若要携带资源，需要后续定义 ZIP/清单签名或 IndexedDB 方案
- `orchestrator.js` 仍偏大，本轮只去除了项目、资源、比例、规范、遮挡和尺寸关系等关键硬编码，完整领域服务拆分属于后续 D6
- 当前研究目录不是 Git 仓库，本轮只能用文件清单和自动测试记录回退边界，不能声称已有独立提交历史
- 助手只有一个，没有做多助手切换。理由见 13-6 第四节：当前只有一类成果，拆成识别助手、制图助手、审核助手只会增加选择成本。等真实项目证明三类任务确实需要不同处理方式再拆
