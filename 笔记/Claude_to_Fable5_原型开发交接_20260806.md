## 五、不要推翻的设计判断

这几条是和用户反复讨论后定下来的，改之前先问。

**出图交给规则程序，不交给模型。** 图纸必须可重复可复测，同样数据每次画出同样结果。模型在这一步只负责把非标准形制翻译成画法参数。

**尺寸核对交给规则程序。** 实测发现同一份数据，`kimi-k2.6` 算出了分间之和与通面阔差 4400mm 的矛盾，`moonshot-v1-128k` 不仅没发现还算错成 2800 并编造了一条假矛盾。换个模型结论就变的事不能进正式成果。

**AI 提议，人确认。** 模型只返回结构化指令，不直接写数据。前端还有三道校验：字段白名单、`editcheck.js` 合理性核对、按钮分“应用无疑问的”和“全部应用”。模型自称的把握不可信，实测它把屋面檐口高从 5200 改成 1200 还标把握高。

**流程编排是确定性状态机，不是 AI 自主规划。** 这是有意的，正式业务里流程顺序必须可预测可审计。文档表述要准确，不能写成“AI 自主推动任务”。

**多助手切换没做。** 理由在 13-6 第四节：当前只有一类成果，拆成识别助手、制图助手、审核助手只增加选择成本。用户没有否掉这个判断。

## 六、踩过的坑

### 模型特性

| 事项 | 实测结论 |
|---|---|
| 正确端点 | `https://api.moonshot.ai/v1`，不是文档写的 `.cn` |
| 浏览器直连 | 通，不需要后端代理 |
| 识别模型 | `kimi-k2.6` 质量最好（76 秒，33 构件，位置框接近人工标注），`moonshot-v1-128k-vision-preview` 快但框粗糙（22 秒，18 构件） |
| kimi 系列识别 | 必须传 `thinking: {type: "disabled"}`，否则跑几分钟且耗尽额度 |
| 推理模型 | 不接受自定义 temperature，只允许 1；正式回答在 `content`，思考在 `reasoning_content`；额度要给够否则回答为空 |
| 服务端 | 会返 429 过载，已做退避重试 |

### 代码层面

- 同源图片不能设 `crossOrigin`，否则要求 CORS 头而 python http.server 不返回，图片直接加载失败。
- 视图里用全局 `Store.sub` 会不断累积回调，必须用 `subView`，切视图时清空。
- `paint()` 重写 `innerHTML` 会把底部操作条一起冲掉，内容区要拆成独立的 `pane-body`。
- 原生 `prompt` 取消返回 `null`，不判断就会让“点取消”变成“确认”。已全部换成 `UI.askText` 和 `UI.askConfirm`。
- 加了卡片一定要写回调，否则用户点了没反应，流程静默卡死。这个错误犯过一次。

## 七、密钥处理

**代码和仓库里不能有明文密钥。** 已建 `.gitignore`，覆盖 `.env*`、`*.key`、含密钥字样的文件名，实测验证过能正确忽略。

密钥只由本地后端的 `.env` 或部署平台环境变量读取，浏览器不保存、不显示密钥。`.env` 已被 Git 忽略，禁止写入代码或提交到仓库。

用户已知这个密钥出现在过对话记录里，计划验收后轮换。

## 九、用户的验收标准

这一点最重要。JIAJIA 会逐条实测并指出问题，标准很高，不接受表面功夫。这次会话被打回过五轮，问题包括：

另外，用户提过一个判断：不要低估 Kimi 的能力，不要手动给它设上限。这次把主流程九个环节改成真实调用后，效果确实比之前好。

## 十、诚实边界

以下几点在文档里已经写明，交接后不要悄悄改成更好听的说法：

- 效率提升目前仍是**产品假设**，不是结论。机器侧数字有了（四个理解类步骤合计 25 秒、2010 token、约 0.02 元），但缺人工基线对照，那只能在真实项目里测。
- 数据校核图是**示意图**，不是符合规范的正式测绘图。
- 位置框由模型给出时精度有限，不能拿它当产品精度。
- 原型只有高都玉皇庙有完整演示数据，另外两个项目是占位。
